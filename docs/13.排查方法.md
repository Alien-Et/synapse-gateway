# 13. 排查方法

## 为什么不能靠猜

上游返回的字段名、错误码、限流文案经常变，而且各家口径不同。
猜出来的「应该就是这样」往往会让你改错地方——真正的根因在另一层。

**先拿到原始响应，再改代码。**

## 四种打印原始响应的方式

按可靠性排序：

### 1. verbose 日志（推荐）

在「我的 → 并发与容错」或设置里打开详细日志，转发时会记录：

- 请求体（已脱敏）
- 响应原文
- 凭证刷新耗时
- 选号过程

### 2. Provider 的 hooks

每个 Provider 构造时可以接 `ProviderHooks`：

```kotlin
ProviderHooks(
    onLog = { line -> ... },
    onVerbose = { payload -> ... },
)
```

适合临时加一行 `hooks.onLog("原始响应：$raw")`。

### 3. 反射调 `android.util.Log`（临时调试唯一可靠路径）

`core` 是纯 JVM 模块，不能直接 `import android.util.Log`，但可以反射调：

```kotlin
runCatching {
    val sample = array.joinToString("\n") { el ->
        val obj = el.takeIf { it.isJsonObject }?.asJsonObject ?: return@joinToString ""
        obj.entrySet().joinToString(" | ") { (k, v) -> "$k=${v.toString().take(120)}" }
    }
    val logClass = Class.forName("android.util.Log")
    val println = logClass.getMethod(
        "println",
        Int::class.javaPrimitiveType,
        String::class.java,
        String::class.java,
    )
    println.invoke(null, 4 /* INFO */, "MY-DEBUG-TAG", "原始条目：\n$sample")
}
```

**为什么需要这条**：另外两条在这两种情况下都读不到 ——

| 方式 | 能否读到 | 原因 |
|---|---|---|
| `hooks.onLog(...)` | ❌ 难 | App 端日志落进加密存储（`EncryptedKeyValueStore` 的 XML），root 也搜不到明文 |
| `System.out.println(...)` | ❌ 不行 | Android 上 stdout 被重定向到 `/dev/null`，不进 logcat |
| **反射调 `android.util.Log`** | ✅ 可行 | 唯一可靠的路径 |

用函数名当 tag（如 `RACCOON-DEBUG`）比通用词好搜，排查完**记得删掉调试代码**。

### 4. 抓包

HTTPS 抓包用 ProxyPin；Android 原生 App 的 HTTPS 流量优先用 Hook 脚本抓
（OkHttp / HttpURLConnection 层），抓不到再上 ProxyPin。

## 看日志

```sh
# 清空缓冲，避免被别的日志挤掉
logcat -c

# 触发一次真实请求（网关在跑的话，直接打接口比点 UI 快）
curl http://127.0.0.1:8790/v1/chat/completions ...

# 立刻搜（用 -b all，main 缓冲可能已滚动）
logcat -b all -d | grep -i "关键词"
```

### 中文/多模式 grep 在 NPmcp 上会失灵

`np_execute_shell` 的中文与多模式 grep 转义有问题。用两步：

```sh
grep -an "关键词" 文件        # 拿行号
sed -n '120,180p' 文件        # 按行号取范围
```

## 字段确认后的收尾

抓到真实字段名之后，三件事必须做完：

1. 把真实字段名写进 [08.上游陷阱清单.md](08.上游陷阱清单.md) —— 下次不用再抓一遍。
2. 用抓到的真实响应结构补一条单测（`withUpstream(path = ..., body = 真实JSON)`），
   锁住解析逻辑，避免以后改崩。
3. 删除调试日志，重新跑 `:core:test` 确认全绿。

## 排查「模型测试失败」

先确认打的是不是正确的端点。模型测试按类型分流（见
[07.端点与透传.md](07.端点与透传.md)），如果类型判错，就会拿对话请求去打
生图/向量端点，上游一律回 400，看着像「模型挂了」。

判断方法：看错误文案。

| 文案 | 说明 |
|---|---|
| `messages 不能为空` | 把对话请求打到了非对话端点 |
| `invalid_request` | 同上，或参数形状不对 |
| `The requested endpoint was not found` | Base URL 与协议对不上 |
| `Invalid URL (POST /...)` | 路径拼错 |
| `model does not exist` | 真的没这个模型 |

## 排查「自定义供应商 404」

按顺序查：

1. Base URL 是否已经含版本段（`/v1`、`/api/paas/v4`）
2. 协议选得对不对（OpenAI 兼容 vs Responses vs Anthropic）
3. 「总是向上游要流式」是否该打开（上游只吃流式时关着会 400）
4. 自定义请求头是否需要（租户号、渠道号、`User-Agent`）
5. 模型 id 是否带前缀（有些站要 `models/xxx`）

## 排查「Cline 报 403 / 402」

这两种都**不是网关的问题**，是上游如实告诉你账号状态。先看错误体里的 `code`：

| 上游 code | 状态码 | 真实原因 | 怎么办 |
|---|---|---|---|
| `ENTITLEMENT_ERROR` + `not subscribed to required model plan` | 403 | **这个账号没订阅 ClinePass** | 换 `cline-free/` 前缀的模型，或去订阅 |
| `insufficient_credits` | 402 | **credit 余额已欠费** | 错误体里带 `current_balance` 和 `buy_credits_url`，照它充值 |
| 其它 403 | 403 | 可能是令牌问题 | 重新登录 |

日志里能直接看到原文（`探测 cline/... 失败（HTTP 403）：{...}`），
把 `message` 和 `current_balance` 读出来就能判断，不用猜。

### ⚠️ 已知坑：token 过期时「刷新额度」会报「拿不到账号 id」

**现象**：点「刷新额度」，余额显示 `—`，detail 写「查询余额失败：拿不到账号 id」。
同时对话本身是好的（对话前会 `refreshAccount` 保鲜）。

**原因**：`GatewayEngine.refreshCredits` **刻意不保鲜**（注释写明「额度刷新本身不保鲜：
动作/对话成功后都会紧接着刷一次额度，这里再保鲜会让同一次动作多打一轮刷新端点」）。
所以 token 一旦过期，「刷新额度」直接拿过期 token 去打 `GET /users/me` → **401**
（错误体：`Unauthorized: Please make sure you're using the latest version of Cline...`），
取不到 `usr-...`，`resolveUserId` 返回空串，于是如实报「拿不到账号 id」。

**怎么确认是这个问题**（实测抓包）：

```
GET /api/v1/users/me          → 401   ← token 的 exp 已过
（等一会儿，对话触发一次 refreshAccount）
GET /api/v1/users/me          → 200   ← 续期后同一个请求就好了
GET /api/v1/users/<usr-id>/balance → 200
```

对照 JWT 里的 `exp` 与请求时间就能定案，不用猜。

**处置**：再点一次「刷新额度」（此时凭证已被对话续期），或直接发一次对话让它续期。
**不要**把它当成「余额查询协议写错了」去改路径 —— 路径是对的，只是 token 过期了。

**排查顺序**：

```
① 看前缀：cline-free/ 还是 cline-pass/ 还是别的
   ├─ cline-pass/  → 需要 ClinePass 订阅，403 ENTITLEMENT_ERROR 是预期的
   ├─ cline-free/  → 免费池，402 说明免费额度用完
   └─ 无前缀（recommended 组，如 google/gemini-4-argon）
                   → 走 credit 计费，402 说明余额欠费
② 看错误体 code
③ 都不是 → 才是网关的问题
```

## 排查「UI 卡住 / 拖不动」

如果是嵌 WebView 的弹窗（人机验证滑块），检查 `AppDialog` 是否传了
`scrollable = false`。默认的 `verticalScroll` 会抢走拖动手势。

## 排查「账号明明有额度却不用它」

池里的额度是上次刷新时的快照。选号规则是「第一轮跳过已知为 0 的，补位轮不跳过」，
所以真正的空号会在补位轮被上游拒一次然后标记。

如果一直是 0 且从不被选，先手动「刷新额度」看是不是真的空。

## 排查「禁用了但不知道原因」

日志卡片上红色「禁用」标签会显示剩余时间。
「我的 → 并发与容错 → 模型禁用」能改阈值与时长。

手动解除单个模型：`ModelBanTracker.unban(providerId, model)`。

## 排查崩溃

```sh
# 应用日志（E 级别）
logcat -d *:E

# 持久化崩溃记录（Java 崩溃、native 崩溃、ANR）
# DropBox / tombstone
```

`anrDetected` / `crashDetected` 都为 false 才算干净。
