# 10. 额度与用量统计

## 额度：必须区分「未知」与「真的用光」

`CreditInfo` 的 `known` 字段：

- `known = true` + `balance = 0`：真的用完了，要充值
- `known = false`：上游没给数或字段没找到，界面显示「—」

**把后者显示成 0 会让人以为额度真的用完了，白充钱。**

## 额度包：回答「还剩多少」

`QuotaPack` 列出该账号的所有额度来源。以灵犀为例：

| 额度包 | 来源 |
|---|---|
| 个人积分 | 主账本 |
| 团队积分 | 团队账本 |
| 当日赠送 | 每日赠送账本 |

三者都要列，只读一个会出现「额度包有 2992、余额还是一万」的不同步。

## 单位换算：只在 Provider 内部做一次

上游给的数**不一定是用户认得的单位**。Cline 是现成的例子：

```
上游 GET /users/{id}/balance  →  {"balance": -17704}
用户界面（Cline 官方）        →  -0.0177 credit
```

差 1e6。官方前端的格式化函数就是 `format(e / 1e6)` —— 上游返回的是**微 credit**。

三条规矩：

1. **换算只在 Provider 内部做一次**，`CreditInfo.balance` 拿到的必须是用户认得的单位。
   调用点不再做二次换算（否则两层换算叠起来，数字差 1e12）。
2. **换算常量只声明一处**（`ClineProvider.MICRO_CREDITS_PER_CREDIT`），
   将来上游改刻度只改这里。
3. **符号如实保留**：`-17704` 是**欠费**，换算成 `-0.0177` 之后仍然是负的，
   界面要能表达「已欠费」——不能取绝对值，那是掩盖事实。

### 不要跨供应商统一单位

Cline 的 credit 与灵犀的积分、商汤的积分**不是一回事**：前者是美元等价的消费额度，
后者是各自平台内的点数。`unit` 写各自的单位（`credit` / `点`），
**不统一成「积分」** —— 统一了会让用户以为可以跨家比较。

## 积分流水：回答「每一笔怎么来的」

`PointsBill` 对齐小浣熊的 `/api/web/points/v1/bills`：
`bill_id` / `event_name` / `biz_type` / `points` / `created_at`。

## 积分与 token：分开统计，不做换算

**这是明确的产品决策**：积分与 token 分别统计，永远井水不犯河水。

原因：缺少可靠的换算口径。硬放一个数是骗用户。
等以后有可靠依据时再补。

首页的「已知额度」面板因此是**双大字并排**——token 总数与积分余额各自大字显示，
齐平对齐，不做换算合并。

### 按账户类型决定显示哪一项

- 没有积分账户 → 只显示 token
- 没有 token 账户 → 只显示积分

## 用量统计

`usage/` 下三个东西：

| 文件 | 内容 |
|---|---|
| `CallLogStore.kt` | 调用记录（每条带请求/响应摘要，按供应商日聚合） |
| `RequestLog.kt` | 运行日志（环形缓冲，300 条） |
| `UsageStats.kt` | 今日/每日/总计 token 与请求数 |

### 调用记录的存储

每条记录带大段请求/响应原文。为了不把内存撑爆：

- 摘要只留前 `MAX_SUMMARY_CHARS` 字符
- 完整原文由 `CappedStringBuilder` 全量统计后另行溢出存盘
- 溢出单字段有上限，正文远超时多出的尾部不再保留

### 日志实时推送

`RequestLog` 用 `addFirst` + 120ms 合并窗口，避免高频日志把主线程刷爆。
界面的自动跟随用 `snapshotFlow` 持续守护，上滑停住、回顶恢复。

## 存储占用

`StorageReport` 列出各类记录与设置的占用，支持自动清理（保留天数 1–3650 天）。
