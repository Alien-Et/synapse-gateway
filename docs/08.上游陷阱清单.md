# 08. 上游陷阱清单

每一条都是实测踩出来的，改动前先读。

## 谷歌 Antigravity —— 凭证铁律

这是本项目踩坑最深的地方，**0.1.40→0.1.57 的「登录频繁失效」全是违反以下原则造成的**。

### 七条正确策略（现行实现）

1. **Provider 内部绝不主动刷新 Token**。`openChat`/`listModels`/`creditInfo` 只调
   `parse(account)` 取当前凭证。
2. **刷新唯一入口**：网关在每次请求前调 `provider.refreshAccount(account, settings.refreshSkewSeconds)`，
   而 `refreshAccount` 内部判断：只在 token 临期 5 分钟内（`REQUEST_SAFETY_WINDOW_SECONDS`）
   才真正调 OAuth。刷新频率天然 ≈ 1 小时 1 次。生效窗口 = `min(skewSeconds, 5min)`，
   故即使全局 `refreshSkewSeconds` 被配大也不会退化成每次请求都刷。
3. **刷新成功必须落盘**：`refreshAccount` 内通过
   `hooks.onAccountUpdated(toProviderAccount(refreshed, account))` 回存 ——
   Google 会轮换 refresh_token，不回存旧值作废后就是永久 `invalid_grant`。
4. **UID 稳定性**：`toProviderAccount(refreshed, existing)` 必须沿用既有账号的 uid，
   否则账号池键漂移 = 账号「消失」。
5. **classify 语义**：401/403 → `SESSION_DEAD`（硬禁用，提示重新登录）。**不要**降级成软重试 ——
   那会让账号很快回来再次触发刷新，形成刷新风暴加速风控。
6. **并发去重**：临期判断在锁外，故锁内必须复查「刚被别的线程刷出的凭证」
   （`lastRefreshed`，按 uid 缓存）并直接复用，否则同一窗口内 N 个在途请求会打出 N 次 OAuth。
   **命中缓存必须返回新凭证而非 null**，否则调用方拿旧 token 直接 401。
   重新登录（`exchangeCode`）要清该 uid 的缓存与冷却，防止旧凭证被回写。
7. **失败冷却**：刷新失败后 60s（`REFRESH_COOLDOWN_SECONDS`，按 uid）内不再重打 OAuth，
   避免 token 被吊销后按请求频率轰炸端点。

### 根因链条（为什么会有这七条）

Google 对同一个 refresh_token 的高频 token 换新有风控。0.1.53~0.1.57 曾在
每次对话前主动刷新 + 401 后「自愈重试」再刷 + 401 降级短冷却回来再刷 ——
三次叠加让一个 token 几分钟内被换新十几次，Google 直接吊销。
表现就是「反复需要重新登录」和后续的 503。

后续又发现两处残留放大器：`refreshAccount` 的临期判断在锁外、锁内不复查最新凭证
（并发 N 请求 = N 次 OAuth），以及刷新失败无退避（token 被吊销后 OAuth 频率 = 请求频率）。
两者均已按上面第 6/7 条堵住。

### 铁律

> 任何「让 Antigravity 更不容易掉线」的改动，如果最终效果是**增加了对
> `oauth2.googleapis.com/token` 的调用频率**，那它一定是错的，无论它看起来多有道理。

**不清空 `access_token`、不改写 `refresh_token`。** 上游用 refresh_token 轮换机制，
一旦你写了空值或把旧的写回去，下一次刷新就永久失效，只能重新登录。

### 另一个坑：对话与配额域名分离

| 用途 | 域名 |
|---|---|
| 对话 | `daily-cloudcode-pa.googleapis.com` |
| 配额查询 | `production-...` |

早期两处都打 daily，导致对话全量 429（daily 的配额小得多）。
配额查询只有 prod 给完整数据。

### 人机验证

需要验证时上游返回 403 `VALIDATION_REQUIRED` 并附 `validation_url`。
界面把它渲染成「一键去验证」，用 Custom Tabs 在应用内打开，验证完自动刷新额度。

## 腾讯（CodeBuddy）—— 强制流式

上游拒绝非流式请求。客户端要非流式时，网关按流式请求、本地聚合成普通 JSON。

### 成长任务的风控

「自动完成任务」有风控风险。埋点里的 `conversationId` 必须指向**真实发出的那次对话**，
自造 UUID 上游不认，进度不计。第一次建议先单条试，不要一上来就点批量。

## 字节（Trae）—— SOLO 私有通道

协议转换最重（15 个文件）。设备指纹用于签到校验，非数字格式会被上游拒绝。

## 讯飞（Loomy）—— HTTP 200 + 业务码

鉴权失败返回的是 **HTTP 200 + 业务码**，不是 4xx。
不判业务码就会把错误 JSON 当正常回复透传，用户看到一段莫名其妙的 JSON。

### 额度有两个账本

- `balance` 是永久账本
- `dailyBalance` 是当日赠送

可用总余额 = 主账本 + 当日剩余。只读一个会出现「额度包有 2992、余额还是一万」的不同步。

## 豆包（doubao）—— 登录混淆 + 凭证判空

豆包是字节自家的 ChatGPT 型供应商，走手机号短信登录（`SmsLoginSupport`，
`authKind=SMS_CODE`），生文/生图/生视频三线路 + 固定窗口。基址
`https://api-normal.doubao.com`，`bot_id=7234781073513644036`。两个易踩的坑：

### `mix_mode=1` 混淆要「编一次、解两次」

登录请求体（`one_login` / `send_code`）在 `mix_mode=1` 时对 `mobile`、
`sms_code_key` 等字段做 **每字节 XOR 0x05** 混淆（`+86` 前缀先拼好再混；
`mobile_ticket`、`sec_uid` 原样不混）。`xorEncode` 只混一次；**回读的
`sms_code_key` 是「混淆值」，要用 `xorDecode` 还原**——而 `xorDecode`
内部要再 XOR 一次 0x05 才得到明文。

早期实现漏了这第二次 XOR，把 `sms_code_key` 原样存下，登录后每次请求都
报鉴权失败。修法见 `DoubaoAuthClient.kt` 的 `xorDecode`（hex→字节后
`xor 0x05`，并加了奇偶长度 / 非法 hex 的防御）。单测锁在真实抓包值上。

### `d_ticket=` 判空别用 `contains`

原始 Cookie 里凭证可能是 `d_ticket = t2...`（等号两边带空格）。用
`cookie.contains("d_ticket=")` 会因空格判成「无凭证」，整串 Cookie 被丢弃。
改成先 `extractCookie(cookie, "d_ticket")` 取出来再 `isEmpty()` 判空
（`DoubaoCredential.kt` 的 `hasTicket` / `parse`）。

### 发码/登录的「HTTP 200 ≠ 成功」

豆包的 `send_code` / `one_login` 在**业务失败时也回 HTTP 200**，真实错误在 body 的
`error_code`（可能包在 `data.error_code`，description 在 `data.description`）。
只判 HTTP 状态码会把「上游拒绝发码」（如 `error_code=7` 访问太频繁）当成「已发送」，
用户点完没收到短信，看起来就是「发送验证码没反应」。`sendSmsCode` / `loginBySmsCode`
都必须解析 body 的 `error_code`，非 0 直接抛 `DoubaoLoginException(description)`。

实测补充：`error_code=7` 不是全局出口 IP 封禁，而是 **`type=24`（登录验证码场景）
+ 账号/设备维度** 的业务频控 —— 换号、隔 1.5 小时、干净 Cookie、去掉
`passport-sdk-*` 头都不变；只把 `type` 改成 25/26 才会穿过 7 到下一层参数校验
（`3052`）。所以它是「稍后再试」，**不是凭证失效**，不要触发重新登录/换号。

### 对话的「HTTP 200 ≠ 成功」：`STREAM_ERROR`

`/chat/completion` 被同一套账号/设备频控命中时，回的是 **HTTP 200 + `text/event-stream`**，
帧序列 `SSE_HEARTBEAT → STREAM_ERROR(710022002「当前服务访问频繁，请稍后再试」)
→ SSE_REPLY_END`。旧版 `DoubaoStreamTranslator.dispatch()` 的 `else -> emptyList()`
把错误帧整帧吞掉，只补一个空 `finish_reason:stop`：流式客户端看到「正常结束但零输出」，
非流式被误报成「豆包返回空回复」——用户永远看不到真正原因。

修法（对齐 TraeSse / RaccoonProvider）：`STREAM_ERROR` 转成 OpenAI 标准顶层
`error` 帧 + `[DONE]`，网关 `parseChunk` 读 `error.message` 记为 FAILED；
`710022002` 映射稳定中文「上游访问频繁，请稍后再试」（抓包里的 `error_msg`
被 Hook 以 latin-1 解成乱码，不能透传），其它码保留上游原文。
翻译器暴露 `failure`（频控码归 `SOFT_RATE`，未知码归 `SERVER`），`DoubaoProvider`
非流式路径返回 `StreamFailureChatCall`，绝不当成「空回复」或 `SESSION_DEAD`。

另：三种头组合（全套 `X-Tt-Token`+tlb-tag+supplement+STUB / 仅 Cookie /
Cookie+STUB）打 `/chat/completion` 响应一字不差 ⇒ **鉴权在 Cookie 层完成**，
`chatHeaders()` 只发 Cookie 足够，不需要补头（实测结论，别凭直觉加）。

### 多账号（`error_code=1454`）—— **选号 token 有两个通道，别只判一个**

一手机号多账号时，候选 `sec_uid` 列表序列化进
`DoubaoMultiAccountException.message`（`MULTI_ACCOUNT|hint|secUid|name|...`）。
因为引擎 `completeSmsLogin` 用 `LoginOutcome(error=message)` 折叠异常，
结构体字段到 UI 层会丢，只能靠 message 透传。

⚠️ **实测断链**（改之前必现）：多账号对话框调的是
`onSmsLogin(id, phone, selMsgid, ccode)` —— 按 `ProviderUiActions` 签名，
第 3 个参数是 **code**，不是 msgid；而 `msgid` 里存的是发码时那份
`encodedMobile`（hex）。旧 `DoubaoProvider.loginBySmsCode()` 只判
`msgid.startsWith("sel:")` ⇒ 选号永远进不来，还把 `sel:xxx` 当验证码 XOR
后发给上游。修法：抽 `DoubaoAuthClient.extractSelToken(msgid, code)` 两个通道
都认（msgid 优先），单测锁死。

同一批候选旧实现**只给第一个账号注册** `pendingMulti` key，用户选第 2/3 个时
`remove()` 必然落空 ⇒ 现在每个候选都注册一份，选中后把同批残留一起清掉。

登录成功后还要校验 `credential.hasTicket`：Set-Cookie 不含 `d_ticket` 时如实报错，
别落一个「能存进去但一调就 401」的废账号。

### 发码头：csrf 不带，guard 头由设备注册链实时生成

真机埋点 `request_csrf_token=0`（发码请求**不带** csrf）、
`response_csrf_token=1`（csrf 是响应才下发的）。早期把
`x-tt-passport-csrf-token` 写死成 hex 值，等于带了不该带的头 —— 已改为空串时
整个头省略。

`bd-ticket-guard-version: 3` 只是**协议版本声明**，不等于这一套齐了。真机实测
`403 → 200` 靠的是补齐 `-iteration-version` / `-tee-status` / `-ree-public-key` /
`-client-cert` / `-server-cert-sn` 等动态票据。这些票据**由设备注册链实时生成**：
`-client-cert` 装的是 **TEE 公钥**（`pub.` 封装，不是证书）、`-ree-public-key` 是
REE 软密钥公钥，两者都是**裸 EC 点**而不是 X.509 SPKI。这点曾被误判成
「网关不可能复刻」，实际走的是公开的 `AndroidKeyStore` API
（完整链路与逐字段抓包对照见 [17.设备证明链与TEE.md](17.设备证明链与TEE.md)）。
剩下的边界只有一条：证书链里的 `attestationApplicationId` 绑定包名与签名摘要，
服务端是否校验只能实测。

纪律不变的是**不写死死值**：过期的写死值只会让 `Bd-Ticket-Guard-Result`
裁决位更差（1103/1104/3），换全新随机指纹则直接 403。现在改成实时生成、
拿不到就整组省略；`DoubaoAuthClient` 的 `DeviceGuardHeaders` 注入口默认空实现，
接不接线都不影响发码逻辑。设备指纹三件套（cdid / iid / device_id）目前仍是固定值，
边界已如实标注，不假装已闭环。

## 商汤（Raccoon）—— 响应包在 data 里

响应外层是 `{"status":..., "data":...}`，字段用标准名（不认 `max_new_tokens`）。

### 刷新策略三级兜底

不再沿用旧过期时间：响应时间 → JWT exp → 30 分钟兜底。
并发锁内复查 + 60 秒失败冷却 + 过期护盾（503 可重试，连续失败超 2 次放开）。

## 灵犀（mCloud）—— 加密请求体

普通接口（发码、登出、刷新 token）无国密，但请求体是
`Base64(IV‖AES-192-CBC)`。`thirdlogin` 是唯一特例（AES-128-ECB + 循环旋转）。

### 额度必须区分「未知」和「真的用光」

残缺 200（没有 `totalTokens`）不能当成 0——那会显示「额度 0」让人以为用完了。
用 `balanceKnown` 区分。

## Cline —— 三道门槛，缺一个就挂

### 1. `X-CLIENT-TYPE` 是免费池的硬门槛

缺了这个头，免费池模型一律 403（`only available via Cline product surfaces`）。
取值必须是 `cline-sdk` —— 写成 `cline-cli` 会让上游走另一条兼容路径，
回 `500 empty response content`，看起来像「模型坏了」。

### 2. `workos:` 前缀不能去掉

`Authorization: Bearer workos:eyJ...`，去掉前缀直接 401。
而 `/auth/refresh` 返回的 accessToken **不带**前缀（登录返回的带），
所以写入前必须统一补 —— 否则续期一次账号就废了。

### 3. `expiresAt` 同名不同型

桌面端 `providers.json` 里是**毫秒数**，`/auth/refresh` 返回的是 **ISO 8601 字符串**
（`"2026-09-19T19:30:04Z"`）。解析不分形态的话，续期一次就把过期时间读成 0，
之后每次请求都以为要刷新。

### 4. 余额路径的账号 id 叫 `external_id`

JWT 里是 `external_id`（`usr-...`），不是 `account_id`。取错字段的后果**不是报错**，
而是 uid 变成空串、路径拼成 `/users//balance`，上游回 `Invalid request format` ——
看起来像「协议写错了」，实际是 id 取错了。

### 5. 403 分两支，别一刀切成「凭证失效」

| 状态 | 归类 | 理由 |
|---|---|---|
| 403 + `ENTITLEMENT_ERROR` | `MODEL_LIMIT` | 这个号对这个模型没权限，换号可能有用 |
| 403 + 其它 | `SESSION_DEAD` | 确实可能是令牌问题 |

归 `SESSION_DEAD` 会硬禁用账号，用户得重新登录才能解封 —— 而权限问题重新登录解决不了。

### 6. 余额是微 credit，欠费是负值

`balance: -17704` 表示 **-0.0177 credit**（已欠费），要 ÷1e6。
上游 402 的文案会直接给出 `current_balance` 和 `buy_credits_url`，可以照抄给用户看。

> ⚠️ **两处口径不同，别混**：余额接口 `/users/{id}/balance` 的 `balance` 是**微 credit**
> （要 ÷1e6）；而 **402 错误体里的 `current_balance` 已经是 credit**
> （实测 `-0.002877`），再除 1e6 会显示成 -0.000002，看着像余额是 0。

### 7. 余额查询会因 token 过期而「拿不到账号 id」

`resolveUserId` 的三级兜底最后一环是 `GET /users/me`，而 token 过期时它回 **401**
（`Unauthorized: Please make sure you're using the latest version of Cline...`）——
于是 uid 取不到、如实报「拿不到账号 id」。

这不是协议错，是**凭证该续期了**。对话路径每次请求前都会 `refreshAccount` 保鲜，
所以对话正常、只有「刷新额度」会撞上（`refreshCredits` 刻意不保鲜）。
详见 [13.排查方法.md](13.排查方法.md) 的「已知坑」。

## 自定义供应商 —— 地址拼接

见 [04.供应商协议层.md](04.供应商协议层.md) 的「地址拼接」。

一句话：**不要先把 Base URL 尾部的 `/v1` 剥掉再贴协议路径**。
模型列表走固定 `/v1/models` 能拉到，对话却会被拼错，上游回
`The requested endpoint was not found`。

## 通用 —— 响应形状

| 现象 | 真实原因 |
|---|---|
| 200 但空 body | 代理吞响应 / 上游静默拒绝，不能当成功 |
| 200 但是 HTML | 登录页被当成了回复，不能透传 |
| 200 但 content 为空 | 空回复，要报可检测的失败 |
| 客户端要流式、上游只回 JSON | 包成 SSE，严格客户端才解析得出 |
