# 06. 账号池与状态

## 存储布局

一个账号一个状态文件，改单个账号只重写它自己的键：

```
account/<供应商>/<账号>              # 凭证（ProviderAccount.toJson）
pool/state/<供应商>/<账号>.json      # 状态（禁用 / 额度 / 优先级）
settings/gateway.json              # 网关设置
settings/provider/<id>.json        # 供应商设置（含 region 等 option）
settings/proxy.json                # 代理设置
settings/custom.json               # 自定义供应商配置
settings/model_blocklist.json      # 模型屏蔽名单
logs/calls/<id>                    # 调用记录
logs/requests.json                 # 运行日志（环形缓冲）
usage/...                          # 用量统计
```

旧版 `pool/state/<供应商>.json`（一个供应商一个文件）首次读取时**惰性迁移**到一账号一文件。

Android 端经 Keystore 加密；命令行端明文存 `~/.aigw`。

**落盘失败必须可见**：加密存储的 `commit()` 失败不抛异常、只返回 `false`
（磁盘满、IO 错误时）。`KeyValueStore.write / writeBatch` 因此返回布尔值，
`AccountPool` 在凭证或状态写不进去时往运行日志写一条
`账号凭证保存失败（供应商/账号）：磁盘写入被拒绝`。

这条不是洁癖：凭证刷新会轮换 `refreshToken`，新值没落盘而旧值已作废，
下次启动就是一次「登录失效」。没有这条日志时，这种故障完全是无声的。

> 调用记录的完整原文（超出 8K 摘要的部分）**不在加密存储里**，而是溢出到
> `cacheDir/call-fulltext/`（单字段 ≤512K 字符、目录总量 ≤64MB）；
> 缓存被系统回收或记录被清理后，详情页回落展示摘要。

## AccountStatus 的字段

| 字段 | 含义 |
|---|---|
| `nickname` | 上游账号资料里的昵称（**会被上游覆盖**） |
| `customName` | 用户自己起的名字（**不会被覆盖**） |
| `displayName` | 派生：`customName > nickname > uid` |
| `credits` / `creditsKnown` | 额度与「是否已知」 |
| `enabled` | 用户手动软开关 |
| `disabled` | 凭证失效导致的硬禁用 |
| `usable` | 派生：`!disabled && enabled` |
| `priority` | 使用优先级 |
| `raised` | 是否被手动提到了默认位置之上 |
| `memberLevel` | 服务器下发的会员身份名 |

### 为什么自定义名单独存

昵称来自上游账号资料，重新登录 / 刷新凭证时会被上游重新下发覆盖。
如果把用户起的名字写进凭证，一次刷新就白改了。

所以 `customName` 单独存在状态文件里，`setCustomName()` 不碰凭证。
**所有展示都该用 `displayName`**，不要各自再写 `nickname.ifEmpty { uid }`——
加了自定义名后每处都要改，漏一处就是「有的地方显示新名字、有的地方还是老昵称」。

### enabled 与 disabled 的区别

- `enabled`：用户手动开关。关掉 = 我不想用这个号。
- `disabled`：凭证失效，系统自动打的标记。打开开关时**同时清掉它**
  （用户显式操作意味着「我重新弄好了」）。

早期 bug：`setEnabled()` 只改 `enabled` 从不清 `disabled`，于是上游 401 判死之后，
手动开关永远打不开。

## 凭证失效之后怎么恢复

两个状态必须分清，它们的恢复路径完全不同：

| 状态 | 谁写的 | 恢复方式 |
|---|---|---|
| `enabled = false`（手动停用） | 用户点开关 | 用户点开关，直接恢复 |
| `disabled = true`（凭证失效） | 上游 401/403 被判 `SESSION_DEAD` | **先鉴权，通过才恢复** |

界面上账号开关的勾选状态是 `usable`（= 未凭证失效 且 未被手动停用），所以凭证失效的
账号会显示成「关」—— 用户看得见问题，也看得见该点哪里。

点开这个关着的开关时，网关不会直接改状态，而是先做一次鉴权探测
（`GatewayEngine.verifyAccount` → `Provider.verifyCredential`，默认走额度查询）：

| 探测结论 | 动作 |
|---|---|
| `VALID`（能读到额度） | 解除硬禁用 + 启用，日志写「账号凭证已恢复可用」 |
| `INVALID`（明确失效措辞 / 401 / 403） | **保持停用**，提示「凭证仍然失效，请重新登录」 |
| `UNSUPPORTED` / `UNKNOWN`（该家不支持探测、网络异常） | **保持停用**，提示无法确认 |

为什么不能一点就恢复：`disabled` 代表「上游明确说这份凭证不行」。直接抹掉它，坏账号会
立刻回到选号池，用户下一次请求又是 401 —— 等于把「重新登录」这个唯一解法藏起来。

为什么探测只认两类证据：读得到额度 = 鉴权通过；明确失效措辞 = 真失效。网络超时、
5xx、看不懂的报错一律算「无法确认」，既不放行也不判死 —— 一次超时不该让用户重新登录，
一次坏凭证也不该被当成好的放回去。

## 导入导出

导出是**快照**，导入按快照原样恢复。文件是 `.agw`（魔数 AGW1 + PBKDF2 + AES-256-GCM），
口令可选。

### 随文件走的内容

| 内容 | 是否导出 |
|---|---|
| 凭证 | ✅ |
| 手动启用/停用、使用优先级 | ✅ |
| 自定义账号名 | ✅（v4 起） |
| 自定义供应商的标签/地址/协议/流式开关/请求头/余额配置 | ✅ |
| 运行时探测出的额度、凭证失效状态 | ❌（导入后重新探） |

### 为什么只认 v3 与 v4

导入是「把快照原样恢复」，缺字段只能靠猜默认值补——猜出来的东西跟你导出时
不是同一份，这种「看起来成功了但其实不一样」比直接报错难查。

- **v1 / v2 拒绝**：缺启用开关与优先级，补默认值会悄悄改掉用户的策略。
- **v3 放行**：只缺 `customName`，而缺失的含义完全确定（跟随上游昵称），
  不存在第二种解释。放行它，用户手上的旧备份不会因为一次升级全部作废。

### 导入即是创建

本机没有的自定义供应商，按文件里的定义建出来；文件没带定义（v1 老文件）就建一个
「地址待填」的占位。

第 3 条是关键：用户的真实诉求就是「本机没创建，所以才要导入」。要是只在
「文件带了定义」时才建，老文件就会变成「没创建 → 导不进去 → 永远创建不了」的死循环。
