# 06. 账号池与状态

## 存储布局

一个账号一个状态文件，改单个账号只重写它自己的键：

```
account/<供应商>/<账号>            # 凭证
pool/state/<供应商>/<账号>.json    # 状态
settings/...                      # 网关、代理、安全、供应商设置
logs/calls/<id>                   # 调用记录
logs/requests.json                # 运行日志（环形缓冲）
usage/...                         # 用量统计
```

Android 端经 Keystore 加密；命令行端明文存 `~/.aigw`。

## AccountStatus 的字段

| 字段 | 含义 |
|---|---|
| `nickname` | 上游账号资料里的昵称（**会被上游覆盖**） |
| `customName` | 用户自己起的名字（**不会被覆盖**） |
| `displayName` | 派生：`customName > nickname > uid` |
| `credits` / `creditsKnown` | 额度与「是否已知」 |
| `enabled` | 用户手动软开关 |
| `disabled` | 凭证失效导致的硬禁用 |
| `usable` | 派生：`!disabled && enabled` |
| `priority` | 使用优先级 |
| `raised` | 是否被手动提到了默认位置之上 |
| `memberLevel` | 服务器下发的会员身份名 |

### 为什么自定义名单独存

昵称来自上游账号资料，重新登录 / 刷新凭证时会被上游重新下发覆盖。
如果把用户起的名字写进凭证，一次刷新就白改了。

所以 `customName` 单独存在状态文件里，`setCustomName()` 不碰凭证。
**所有展示都该用 `displayName`**，不要各自再写 `nickname.ifEmpty { uid }`——
加了自定义名后每处都要改，漏一处就是「有的地方显示新名字、有的地方还是老昵称」。

### enabled 与 disabled 的区别

- `enabled`：用户手动开关。关掉 = 我不想用这个号。
- `disabled`：凭证失效，系统自动打的标记。打开开关时**同时清掉它**
  （用户显式操作意味着「我重新弄好了」）。

早期 bug：`setEnabled()` 只改 `enabled` 从不清 `disabled`，于是上游 401 判死之后，
手动开关永远打不开。

## 导入导出

导出是**快照**，导入按快照原样恢复。文件是 `.agw`（魔数 AGW1 + PBKDF2 + AES-256-GCM），
口令可选。

### 随文件走的内容

| 内容 | 是否导出 |
|---|---|
| 凭证 | ✅ |
| 手动启用/停用、使用优先级 | ✅ |
| 自定义账号名 | ✅（v4 起） |
| 自定义供应商的标签/地址/协议/流式开关/请求头/余额配置 | ✅ |
| 运行时探测出的额度、凭证失效状态 | ❌（导入后重新探） |

### 为什么只认 v3 与 v4

导入是「把快照原样恢复」，缺字段只能靠猜默认值补——猜出来的东西跟你导出时
不是同一份，这种「看起来成功了但其实不一样」比直接报错难查。

- **v1 / v2 拒绝**：缺启用开关与优先级，补默认值会悄悄改掉用户的策略。
- **v3 放行**：只缺 `customName`，而缺失的含义完全确定（跟随上游昵称），
  不存在第二种解释。放行它，用户手上的旧备份不会因为一次升级全部作废。

### 导入即是创建

本机没有的自定义供应商，按文件里的定义建出来；文件没带定义（v1 老文件）就建一个
「地址待填」的占位。

第 3 条是关键：用户的真实诉求就是「本机没创建，所以才要导入」。要是只在
「文件带了定义」时才建，老文件就会变成「没创建 → 导不进去 → 永远创建不了」的死循环。
