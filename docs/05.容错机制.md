# 05. 容错机制

## 三层防线

```
① 换号
   同一个区域里，换下一个账号重试
   ↓ 这个区域的所有号都试过了
② 跨区域（可选，默认开启）
   换到同一家供应商的另一个区域
   ↓ 两个区域都没号能用
③ 放弃，如实报错
   绝不改发别家供应商
```

另有第四套**默认关闭**的跨供应商转移，见文末。

## 两套容易混的机制：冷却 vs 禁用

| | 冷却 `ModelCooldownTracker` | 禁用 `ModelBanTracker` |
|---|---|---|
| 粒度 | 供应商 + **账号** + 模型 | 供应商 + 模型（**全账号**） |
| 时长 | 10 分钟（可调） | 默认 24 小时（**可调**） |
| 触发 | 一次模型级限流 | **解封后当天仍连续失败 N 次** |
| 落盘 | 否（瞬态） | **是**（重启后依然禁用） |
| 语义 | 「这个号用这个模型暂时不行」 | 「这个模型这阵子别用了」 |

### 为什么需要禁用

冷却只能挡住「这一个号」，换个号又去撞同一个模型。如果上游对这个**模型**整体
有长时间问题（配额池耗尽、模型下线、账号被该模型风控），换号是白费力气：
每次都要试一遍、每次都失败、每次都要等一轮超时。禁用是「认输并记住」。

### 禁用的两个参数都可调

「我的 → 并发与容错 → 模型禁用」：

| 参数 | 范围 | 默认 |
|---|---|---|
| 连续失败阈值 | 1–20 次 | 3 |
| 禁用时长 | 1 小时 – 30 天 | 24 小时 |

禁用期间该模型不再被路由，客户端继续点名它会直接走故障转移。
禁用成功后发横幅 + 常驻通知，**只提醒一次**；日志卡片上标红色「禁用」。

## 冷却的提醒策略

「冷却提醒只一次」：同一模型在冷却期内只提醒第一次，后续静默走故障转移。
关掉这个开关的话每个命中冷却模型的请求都会弹一次，批量请求时能把屏幕刷满。

## 熔断（供应商级）

与冷却/禁用不同，熔断是**整家供应商**级别的：

| 参数 | 说明 |
|---|---|
| 连续失败阈值 | 默认 5 次 |
| 熔断静默时长 | 默认 60 秒 |
| 半开恢复成功数 | 默认 2 次 |

**供应商熔断不等于账号熔断**：只有「整轮所有号都失败」才会给供应商记一次失败，
某个号反复出错不会连累整家。

## 并发闸门

两个上限，都可以设 0 = 不限：

| 参数 | 作用 |
|---|---|
| 单账号在途上限 | 同一个账号同时最多几个请求 |
| 全局在途上限 | 所有供应商合计最多几个请求 |

**选号与取许可原子绑定**：拿不到许可时不标记账号为已尝试，后续重试还能选它。
早期版本先选号再取许可，选完拿不到许可就白丢了一个候选。

## 跨供应商转移（默认关闭）

独立模块 `CrossProviderFailover.kt`，与前三层并列。

开启后：当前供应商熔断、账号全不可用或持续失败时，改发用户勾选的候选模型。
**这会打破「写哪家发哪家」的预期**，所以默认关闭，且开启后必须手动配候选。

三种策略：按顺序、随机、按额度（读缓存，不为排序额外请求上游）。

## 请求体上限

**默认关闭 = 完全不限大小、不限并发。**

打开开关后才启用方案 B：

| 参数 | 范围 | 默认 |
|---|---|---|
| 单条请求体上限 | 8–256 MB | 32 MB |
| 同时接收并发数 | 1–8 条 | 2 |

超出同时接收数的请求直接返回 429，不排队。内存峰值约为「上限 × 并发数 × 3」。
