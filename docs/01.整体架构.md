# 01. 整体架构

## 这个软件是什么

把手机里多个 AI 服务账号（腾讯、字节、谷歌、讯飞、商汤、ChatGPT，以及用户自己加的中转站），
统一成一个 **OpenAI 兼容接口**，在本地 `127.0.0.1:8790` 上提供。

任何支持 OpenAI 协议的客户端（Cline、Cherry Studio、Continue、curl）都能直接调用，
不用关心背后是哪家、有几个号、哪个号还有额度。

## 三个模块

| 模块 | 类型 | 职责 |
|---|---|---|
| `:core` | 纯 JVM | 网关引擎、HTTP 服务、账号池、路由、各供应商协议、存储抽象 |
| `:app` | Android | Compose UI、前台服务保活、加密存储、控制中心磁贴 |
| `:cli` | 纯 JVM | 命令行工具，不开 App 也能联调 |

`core` 不依赖 Android，所以 900+ 个单元测试能在纯 JVM 上跑完，不用真机。

## 一次请求的生命周期

```
客户端 (Cline / Cherry Studio / curl)
   │  POST /v1/chat/completions  {model: "标签/模型名", ...}
   ▼
GatewayHttpServer   ① 鉴权  ② 解析 model
   ▼
GatewayEngine       ③ 按标签解析路由（唯一确定一家）
                    ④ 选号（跳过已冷却 / 已停用 / 已知额度为 0 的号）
                    ⑤ 失败换号 → 本区域试完才跨区域 → 仍不行就如实报错
                       全程不跨供应商
   ▼
Provider 实现       上游私有协议 ⇄ OpenAI 协议（转换全封在 Provider 内）
   ▼
上游 API
```

## 核心不变量

**Provider 的边界是「OpenAI 进、OpenAI 出」。**

上游协议细节（Anthropic 的 `messages`、Gemini 的 `:generateContent`、Codex 的
`/responses` 事件流）不得泄漏到网关层。网关只认 `ChatCall` 这一种返回类型。

这条不变量是整个项目可维护性的根基：加一家新供应商，只写一个 Provider，
路由、选号、重试、冷却、熔断、日志、保活全都自动获得。

## 分层职责

| 层 | 文件 | 只负责 |
|---|---|---|
| HTTP 层 | `gateway/GatewayHttpServer.kt` | 解析请求、鉴权、选号、转发、写记录 |
| 引擎层 | `gateway/GatewayEngine.kt` | 路由解析、账号池协调、额度、任务、导入导出 |
| 协议层 | `provider/*/` | 上游协议 ⇄ OpenAI 的转换 |
| 状态层 | `pool/AccountPool.kt` | 账号凭证、额度、启用状态、优先级 |
| 容错层 | `failover/` | 冷却、禁用、熔断、并发闸门、跨供应商 |

**不要跨层调用**：HTTP 层不直接读账号池文件，Provider 不认识路由标签，
容错层不关心请求内容。

## 数据流方向

```
客户端 ──→ GatewayHttpServer ──→ GatewayEngine ──→ Provider ──→ 上游
                │                     │
                │                     └──→ AccountPool（选号、状态）
                │
                └──→ CallLogStore / RequestLog（记录、日志）
```

状态变化（额度、冷却、禁用）从 Provider 回传到 Engine，再落到 AccountPool 与
各个 Tracker；**不反向**——Provider 不会主动改路由决策。
