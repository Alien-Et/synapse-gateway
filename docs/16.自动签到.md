# 16. 自动签到

「到点自动签到」听起来只是加个定时器，实际上有四个必须想清楚的点：**默认该开还是关**、
**两条触发路径怎么不打架**、**时区与跨天怎么算**、**提醒在前台/后台分别怎么发**。
这一篇把它们写清楚，顺便记下实施时踩到的一个坑。

## 默认关（这是有意的）

本项目最硬的一条纪律是「不替用户做决定」：标签不猜、模型不静默替换、额度未知不显示 0。
**按天主动向上游发起签到属于同一类事** —— 没打招呼就替他去签到，和他自己点「一键签到」
是两回事。所以 `onLaunchEnabled` 与 `scheduledEnabled` **默认都是关**。

## 两条触发路径，共用一次执行

| 路径 | 什么时候跑 | 开关 |
|---|---|---|
| 启动时 | 当天第一次打开 App（`MainActivity.onResume` → `onAppForeground`） | `onLaunchEnabled` |
| 定时 | App 挂后台、到点（网关服务内的排程） | `scheduledEnabled` |

两条路**共用一个「今天已跑过」的日期键**（`auto/checkin_last_day`），所以不会出现
「23:59 开 App 签一次、00:01 闹钟又签一次」。判断落在 `GatewayEngine.runAutoCheckin()`：

1. 先比日期键；今天已跑过就直接返回；
2. 没跑过就**先落盘再执行** —— `store.write` 在 App 端是同步的（加密存储必须同步），
   所以落盘那一刻起今天就被标记为已跑，重入与并发都被挡住。

**落盘而不是放内存**是必须的：只放内存的话用户重启一次 App 就重新签一遍。

「定时」那条排在进程内（复用 `GatewayEngine` 的共享 `scheduler`），
**不用 AlarmManager** —— 也就没必要申请 `SCHEDULE_EXACT_ALARM` 这个敏感权限。
代价如实写在界面上：**进程被杀或手机重启后不会触发**（网关刻意 `START_NOT_STICKY`
不自重建，自重建是灰色软件特征）。

## 时区：必须用本地日期，不能用 UTC 天数

`GatewayEngine.autoPurgeIfDue()` 用的是 UTC 天数（`nowMillis() / DAY_MILLIS`），
那是给**日志清理**用的，晚一天没影响。

「凌晨 00:00 签到」是**本地时间**的概念：东八区 00:05 签到，UTC 那边还是前一天 16:05。
用 UTC 天数会把它算成「昨天已经跑过」，于是当天不再跑 —— 恰恰把功能吃掉。
所以一律按 `AutoCheckinPlan.localDate()` 的本地日期字符串做键。

## 抖动：避开整点

整点批量签到是最典型的机器特征。当天在 `[设定时刻, 设定时刻 + 抖动)` 内取一个**固定**时刻：

- 由日期字符串派生（`AutoCheckinPlan.jitterFor`），**同一天恒定、不需要持久化** ——
  重算多少次都一样，重启也不会漂；
- 默认 30 分钟、上限 120 分钟；
- 设 0 表示不抖动（想要整点的人可以关掉）。

## 只作用于「可用」的账号

`autoCheckinTargets()` 三道过滤缺一不可：

1. 供应商声明了 `ProviderCapability.CHECKIN`；
2. 账号 `usable`（**未被手动停用、凭证未失效**）—— 用户手动停用的号必须排除，
   绕过去替他签到等于把他的开关当摆设；
3. `supportsAction(..., ACTION_CHECKIN)` —— 区域型供应商的国际版、企业账号本就没有签到入口。

签到完的额度刷新不用另写：`performActionAll` 在动作成功后会统一补刷一次额度。

## 登录新账号后的检查（与自动签到同一条链路）

`GatewayEngine.adopt()` 是**所有登录成功的唯一出口**，所以「首次登录」天然有钩子，
不需要额外状态。`checkNewAccountDailyStateSoon()` 异步做三件事：

1. **签到**：直接打一次（上游签到接口幂等，它自己会说「今日已签到」）；
2. **任务**：只**读**一遍任务列表，有没做完的就提示用户 —— 不自动做；
3. **自动做任务**：只有 `autoCompleteTasksOnLogin` 打开、且供应商支持
   `TASK_AUTO_COMPLETE` 时才做，**默认关**。

第 2/3 步分开是刻意的：自动做任务要模拟真实对话埋点，埋点里的会话 id 必须指向
真实发出的对话，自造 id 上游不计进度（见 [08.上游陷阱清单.md](08.上游陷阱清单.md)
的「成长任务的风控」）。**签到与任务检查始终执行，不受那个开关影响。**

## 提醒：前台弹窗、后台通知

`SystemPrompt`（Toast / 对话框）**必须有前台 Activity**，App 在后台会抛
`BadTokenException`。所以自动签到的结果**只走系统吐司总线**（`NoticeEvents` →
`GatewayNoticeNotifier`），前后台都安全；用户在前台时它就是一条 Toast，在后台时
由系统的通知体系承接。不做「盖在别的 App 上」的真悬浮窗 —— 那要常驻
`SYSTEM_ALERT_WINDOW`，既费电又是灰色软件特征。

日志里同时留一条 `自动签到完成：N 个账号成功，额度已刷新` / `自动签到部分失败：…`，
失败会列出**是哪个账号、什么原因**。

## ⚠️ 实施踩到的坑：新增 AppUiState 字段要改四处

第一版「开关打不开、时间改不了」，**引擎其实已经写进去了**（日志里能看到
`自动签到设置已更新（启动时=开…）`），但界面永远显示关。

原因：`AppUiState` 的新字段只加了三处，漏了 `refresh()` 里那个
`_state.value = current.copy(...)`。`copy()` 有默认值，**漏字段编译不报错**，
结果是界面永远读初始值。

> **新增 AppUiState 字段必须同时改四处**：
> ① `AppUiState` 字段声明；② `Snapshot` 数据类；③ `Snapshot(...)` 构造调用；
> ④ `refresh()` 里的 `current.copy(...)`。

另外界面上**不要**用整块替换的 `updateAutoCheckinSettings(updated)`：
界面拿到的 `state` 是上一次 refresh 的快照，连续快速切两个开关时第二次会把第一次
覆盖掉（真机实测过）。界面一律用 `setAutoCheckinXxx()` 这些单字段方法 ——
它们在写入那一刻从引擎读当前值再合并。

## 涉及的代码

| 文件 | 职责 |
|---|---|
| `core/gateway/AutoCheckinSettings.kt` | 偏好（两个开关 + 时刻 + 抖动 + 自动做任务） |
| `core/gateway/AutoCheckinPlan.kt` | 纯时间计算：本地日期、抖动、下一次目标时刻 |
| `core/gateway/GatewayEngine.kt` | 当天去重、目标选择、执行、排程、登录后检查 |
| `app/ui/AutoCheckinScreen.kt` | 设置页（两个开关 + 修改时刻弹窗 + 登录后开关） |
| `app/service/GatewayService.kt` | 排程跟着网关生命周期启停 |
