# 04. 供应商协议层

## 唯一不变量

**OpenAI 进、OpenAI 出。**

网关只认 `ChatCall` 这一种返回类型。上游是 Anthropic 的 `messages`、
Gemini 的 `:generateContent`、还是 Codex 的 `/responses` 事件流，
差异全部封在各自 Provider 内部，不泄漏到网关层。

## Provider 接口

```kotlin
interface Provider {
    val id: String
    val displayName: String
    val capabilities: Set<ProviderCapability>

    fun listModels(account: ProviderAccount?): ProviderModelCatalogView
    fun resolveModel(requested: String): String
    fun openChat(account: ProviderAccount, openAiBody: String): ChatCall
    fun creditInfo(account: ProviderAccount): CreditInfo?
    fun performAction(account, action, payload): ProviderActionResult
    fun taskList(account): ProviderTaskListView?
    fun passthrough(account, method, path, body): ChatCall?
    val passthroughPaths: Set<String>
    fun refreshAccount(account, skewSeconds): ProviderAccount?
}
```

新增一家供应商 = 实现这个接口 + 在 `ProviderBootstrap` 登记 + 在 `app/ui/providers/`
加一个 `ProviderUi` + 标签表加一条。路由、选号、重试、冷却、熔断、日志、保活全部自动获得。

## 三家协议转换最重的

### 字节（Trae）—— SOLO 私有通道

请求体、响应体、工具 schema 全都不是 OpenAI 形状，转换代码最多。
`trae/` 子包 16 个文件。

### 腾讯（CodeBuddy）—— 强制流式

上游拒绝非流式请求。网关的做法：客户端要非流式时，仍按 `stream:true` 请求，
拿到 SSE 后本地聚合成普通 JSON 返回。

### ChatGPT —— Responses API

`/responses` 与 `/chat/completions` 完全不兼容：

| | Chat Completions | Responses |
|---|---|---|
| 消息 | `messages[]` | `input[]` |
| system 角色 | `system` | `developer` |
| 必填字段 | — | `store: false`、`include: ["reasoning.encrypted_content"]` |
| 流事件 | `chat.completion.chunk` | `response.output_text.delta` 等 |

转换在 `chatgpt/OpenAiResponses.kt`：
- `toResponsesRequest()`：客户端请求 → Responses 请求
- `SseTranslator`：Responses 事件 → `chat.completion.chunk`

**这套转换现在也被自定义供应商复用**（见下）。

## 自定义供应商

用户填 Base URL + API Key，走 `custom/CustomProvider.kt`（单文件）。

### 协议表决定四件事

`gateway/ProviderProtocols.kt` 里的 `ProviderProtocol`：

| 字段 | 作用 |
|---|---|
| `chatPath` | 对话端点路径 |
| `modelsPath` | 模型列表路径 |
| `auth` | 鉴权方式（Bearer / x-api-key / ?key=） |
| `requestShape` | 请求体形状（CHAT 的 `messages` / RESPONSES 的 `input`） |
| `forceStreaming` | 上游是否只吃流式 |

当前支持的协议：OpenAI 兼容、**OpenAI Responses**、Anthropic、Gemini、智谱、
百炼、火山方舟、Cohere、DeepSeek、Moonshot。

### 地址拼接：`joinBaseAndPath()`

中转站和官方文档对 Base URL 的写法不统一，四种都要拼对：

| 用户填的 Base URL | 协议路径 | 结果 |
|---|---|---|
| `https://x.com` | `/v1/chat/completions` | `https://x.com/v1/chat/completions` |
| `https://x.com/v1` | `/v1/chat/completions` | `https://x.com/v1/chat/completions`（重叠段只留一次） |
| `https://x.com/v1` | `/chat/completions` | `https://x.com/v1/chat/completions`（**保留**用户写的版本段） |
| `https://open.bigmodel.cn/api/paas/v4` | `/api/paas/v4/chat/completions` | 不重复 |

**关键教训**：以前先 `removeSuffix("/v1")` 再贴协议路径。模型列表走固定
`/v1/models` 能拉到，对话却被拼到 `/chat/completions` 或
`/api/paas/v4/api/paas/v4/...`，上游回 `The requested endpoint was not found`，
而网关一律当成「没有这个模型」——模型 id 其实没问题，换个客户端就能用。

### 404 分类

```
404 + 文案含 endpoint / invalid url / no route / 接口不存在
  → ErrorKind.CLIENT，提示「Base URL 和协议对不上」
404 + 其它（如 model does not exist）
  → ErrorKind.NOT_FOUND，提示「上游没有这个模型」
```

## 模型端点识别

模型测试要按类型打对应端点，否则一律 400。识别逻辑在
`provider/ProviderModels.kt` 的 `ProviderModel.endpointKind`：

| 端点 | 判定依据 |
|---|---|
| 图片生成 | `tags`/`category`/`ability` 含 image，或 id 含 `seedream`/`dall-e`/`image` 等 |
| 视频生成 | 同上含 video，或 id 含 `veo`/`sora`/`kling`/`seedance` |
| 文本向量 | 同上含 embed，或 id 含 `bge-`/`text-embedding` |
| 重排 | 同上含 rerank，或 id 含 `rerank` |
| 语音转写 | id 含 `whisper`/`transcribe`/`asr` |
| 语音合成 | id 含 `tts`/`text-to-speech` |
| 对话 | 以上都不是 |

**顺序有讲究**：重排必须排在向量前面——`bge-reranker-v2` 同时命中 `bge-` 与
`rerank`，按向量先判就会把重排模型打去 `/v1/embeddings`。

**识图不算生图**：`vision`/`vl`/`vlm`/`understand` 先被排掉，不会被 `image`
兜底词根误判。这类模型走的是对话端点。
