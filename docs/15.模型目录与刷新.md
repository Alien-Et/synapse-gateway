# 15. 模型目录与刷新

模型目录不是「一个接口拉一次」那么简单：八家供应商各有各的目录来源、缓存策略与失败形态，
界面还要在**不阻塞用户**的前提下逐家点亮。这一篇讲清楚整条链路。

## 目录从哪来

| 供应商 | 目录来源 | 有缓存吗 |
|---|---|---|
| 谷歌（Antigravity） | 上游模型清单 | 10 分钟 TTL，失败回落上次成功结果 |
| 字节（Trae） | 客户端 product config | 内存缓存，失败回落 |
| 腾讯（CodeBuddy） | 国内走网页控制台 / 国外走客户端 product config | 无缓存，每次真打 |
| 讯飞（Loomy） | 上游模型接口（倍率内嵌在 name 里） | 内存缓存，失败回落 |
| 商汤（Raccoon） | `/api/web/llm/v2/model_catalog` | 无缓存 |
| 灵犀（mCloud） | 登录时随 apikey 一起落盘 | 落盘（`listModels` 不打上游） |
| ChatGPT | `/models` | 30 分钟 TTL |
| Cline | `GET /ai/cline/recommended-models`（**无鉴权可拉**） | 无缓存 |
| 自定义 | 用户保存时抓到的清单 | 落盘 |

「无缓存」不等于每次刷新都慢：目录拉取是**并行**的，最慢那家决定整体时长。

## 流式加载：每家就绪就点亮

`GatewayEngine.modelsStreaming(forceRefresh, onChunk)` 是模型页的数据入口：

- 每个供应商一个后台任务，**就绪立即回调** `ProviderModelsChunk(providerId, models, error?)`；
- 不等最慢的那家 —— 整体耗时从「最慢者」降到「最快者即可见」；
- 阻塞聚合版 `models()` 只是丢弃回调、取最终结果（供 `/v1/models`、CLI 使用）。

`forceRefresh = true`（模型页的刷新按钮）会**先**调各 provider 的 `invalidateModelCache()`
丢弃 TTL 缓存，保证这次真的重打上游。不这么做的话，刷新按钮会命中缓存，
远端已下架的模型仍滞留在列表里 —— 用户点了刷新却什么都没变。

## 界面状态字段

`AppUiState` 里与目录相关的字段：

| 字段 | 含义 |
|---|---|
| `modelsLoading` | 是否有一轮流式加载在进行 |
| `modelLoadStates` | 每个供应商的进度：`Loading` / `Done(count)` / `Failed(reason)`；发起时先全部置 `Loading` |
| `models` | 各供应商就绪即增量合并（同供应商旧条目被替换）；一轮结束时整体覆盖为最终聚合 |
| `modelsError` | 整体异常 + 各失败供应商汇总（`供应商：原因`） |
| `modelCatalogChanges` | 本轮相对上一轮的**新增 / 移除**（见下） |

`AppViewModel.refreshModels` 用**代次**（`modelsGeneration`）防并发错乱：
用户连点刷新时，只有最新那一轮的增量会被写进 state。

发起刷新时若已有旧目录，本次降级为**静默刷新**：不弹全屏 busy，旧数据先可见、
新数据逐组替换。只有首次加载（`models` 为空）才显示骨架屏。

## 云端目录变更检测

上游会增删模型：新上架、下架、限免活动结束、账号换套餐……用户看到的只是「列表变了」，
不知道变了什么，也就无从判断「我配的模型怎么不见了」。

`ModelCatalogChanges.of(previous, current, refreshedProviders, firstLoad)` 在每轮刷新后比较：

- **只比较本轮真的拉到目录的供应商**（`refreshedProviders`）。
  拉取失败（无账号、上游故障、超时）**不参与比较** —— 否则一次网络抖动就会把整家供应商
  的模型判成「已移除」，用户看到的是一次假下架。这与「未知 ≠ 零」是同一条纪律。
- 首次加载（`previous` 为空）一律视为无变更：没有基准可比，报「新增 200 个」毫无意义。
- 结果按供应商聚合，界面提示一次、同时写进运行日志（模型页的提示是一闪而过的，
  日志能回看「哪天少了什么」）。
- 摘要只报数量（`Cline 新增 2、移除 1`），不铺开几十个模型名。

变更**不落盘**：它是「本次刷新的观察结果」，重启后没有意义。

## 失败不算下架

拉取失败的处理有两层，都在 `GatewayEngine`：

1. **没有账号不算失败**：登录前本就不该有模型，供应商自报的 error 也不报红 ——
   否则未登录的供应商会在模型页显示「拉取模型目录时有报错：未登录」，看着像故障。
2. **有账号却失败**：这是真的拉取失败（网络/协议/解析），必须报给用户。

单家超时（`MODELS_FETCH_TIMEOUT_SECONDS = 20s`）只让那一组失败，不影响其它家。

## 开放名单与自动清理

`ModelExposureSettings` 是「对外暴露哪些模型」的白名单（`filterEnabled` 关闭时原样放行）。

刷新后 `pruneStaleExposure` 会清掉远端已不存在的模型：

- 只处理**本轮真的拉到了模型**的前缀；
- 拉不到时目录可能只是暂时取不到，**不能凭此抹掉用户的勾选**。
