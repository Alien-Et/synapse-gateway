# 15. 模型目录与刷新

模型目录不是「一个接口拉一次」那么简单：八家供应商各有各的目录来源、缓存策略与失败形态，
界面还要在**不阻塞用户**的前提下逐家点亮。这一篇讲清楚整条链路。

## 目录从哪来

| 供应商 | 目录来源 | 有缓存吗 |
|---|---|---|
| 谷歌（Antigravity） | 上游模型清单 | 10 分钟 TTL，失败回落上次成功结果 |
| 字节（Trae） | 客户端 product config | 内存缓存，失败回落 |
| 腾讯（CodeBuddy） | 国内走网页控制台 / 国外走客户端 product config | 无缓存，每次真打 |
| 讯飞（Loomy） | 上游模型接口（倍率内嵌在 name 里） | 内存缓存，失败回落 |
| 商汤（Raccoon） | `/api/web/llm/v2/model_catalog` | 无缓存 |
| 灵犀（mCloud） | 登录时随 apikey 一起落盘（`apikey/get` 给倍率；`chat/config/get` 补上下文与能力） | 落盘（`listModels` 不打上游，老账号首次补齐时例外） |
| ChatGPT | `/models` | 30 分钟 TTL |
| Cline | `GET /ai/cline/recommended-models`（**无鉴权可拉**） | 无缓存 |
| 自定义 | 用户保存时抓到的清单 | 落盘 |

「无缓存」不等于每次刷新都慢：目录拉取是**并行**的，最慢那家决定整体时长。

## 流式加载：每家就绪就点亮

`GatewayEngine.modelsStreaming(forceRefresh, onChunk)` 是模型页的数据入口：

- 每个供应商一个后台任务，**就绪立即回调** `ProviderModelsChunk(providerId, models, error?)`；
- 不等最慢的那家 —— 整体耗时从「最慢者」降到「最快者即可见」；
- 阻塞聚合版 `models()` 只是丢弃回调、取最终结果（供 `/v1/models`、CLI 使用）。

`forceRefresh = true`（模型页的刷新按钮）会**先**调各 provider 的 `invalidateModelCache()`
丢弃 TTL 缓存，保证这次真的重打上游。不这么做的话，刷新按钮会命中缓存，
远端已下架的模型仍滞留在列表里 —— 用户点了刷新却什么都没变。

## 本机 last-known-good 缓存与自动刷新

模型页目录还会在 App 的加密键值存储中按供应商保存一份**上次成功目录**，键为
`catalog/models.<providerId>`。这是 Magpie「保留最后一次成功模型清单」策略在多供应商网关中的适配：
目录来自各 Provider 自己的接口/账号，不会拿 `models.dev` 的通用目录冒充某家真实可用模型。

- 冷启动先展示本机上次成功副本，条目标记 `cached=true` 并显示「缓存」，不会假装是实时结果。
- 成功拉取才覆盖对应供应商副本；失败、超时或部分区域失败时保留上次成功副本，且仍显示错误原因。
- 成功目录超过 30 分钟后，在 App 回到前台或进入模型页时静默后台刷新；用户不必手动刷新。
- 刷新失败后至少等待 5 分钟才允许下一轮自动重试，避免每次切前台都请求上游。
- 某供应商本轮成功返回空目录时会清空它的旧副本；否则旧模型会被误当成仍在目录中。
- 同一目录同时服务模型页与网关 `/v1/models`；`modelCatalogSnapshot` 仍是进程内故障转移快照，重启后由下一轮加载重建。

目录存在 ≠ 当前请求一定成功：缓存仅用于「上游暂时不可达时先保留已知清单」，不能代替真实测速或在线调用验证。

## 界面状态字段

`AppUiState` 里与目录相关的字段：

| 字段 | 含义 |
|---|---|
| `modelsLoading` | 是否有一轮流式加载在进行 |
| `modelLoadStates` | 每个供应商的进度：`Loading` / `Done(count)` / `Failed(reason)`；发起时先全部置 `Loading` |
| `models` | 各供应商就绪即增量合并；失败供应商保留 last-known-good 副本，成功供应商替换为本轮目录 |
| `modelsError` | 整体异常 + 各失败供应商汇总（`供应商：原因`） |
| `modelCatalogChanges` | 本轮相对上一轮的**新增 / 移除**（见下） |

`AppViewModel.refreshModels` 用**代次**（`modelsGeneration`）防并发错乱：
用户连点刷新时，只有最新那一轮的增量会被写进 state。

发起刷新时若已有旧目录，本次降级为**静默刷新**：不弹全屏 busy，旧数据先可见、
新数据逐组替换。只有首次加载（`models` 为空）才显示骨架屏。

## 云端目录变更检测

上游会增删模型：新上架、下架、限免活动结束、账号换套餐……用户看到的只是「列表变了」，
不知道变了什么，也就无从判断「我配的模型怎么不见了」。

`ModelCatalogChanges.of(previous, current, refreshedProviders, firstLoad)` 在每轮刷新后比较：

- **只比较本轮真的拉到目录的供应商**（`refreshedProviders`）。
  拉取失败（无账号、上游故障、超时）**不参与比较** —— 否则一次网络抖动就会把整家供应商
  的模型判成「已移除」，用户看到的是一次假下架。这与「未知 ≠ 零」是同一条纪律。
- 首次加载（`previous` 为空）一律视为无变更：没有基准可比，报「新增 200 个」毫无意义。
- 结果按供应商聚合，界面提示一次、同时写进运行日志（模型页的提示是一闪而过的，
  日志能回看「哪天少了什么」）。
- 摘要只报数量（`Cline 新增 2、移除 1`），不铺开几十个模型名。

变更**不落盘**：它是「本次刷新的观察结果」，重启后没有意义。

## 失败不算下架

拉取失败的处理有两层，都在 `GatewayEngine`：

1. **没有账号不算失败**：登录前本就不该有模型，供应商自报的 error 也不报红 ——
   否则未登录的供应商会在模型页显示「拉取模型目录时有报错：未登录」，看着像故障。
2. **有账号却失败**：这是真的拉取失败（网络/协议/解析），必须报给用户。

单家超时（`MODELS_FETCH_TIMEOUT_SECONDS = 20s`）只让那一组失败，不影响其它家。

## 屏蔽名单

`ModelBlocklist`（`settings/model_blocklist.json`）记录本机不想再用的模型，
**被动排除**——「这些模型已知坏了，别再碰」。

被屏蔽的模型在三处同时生效：

1. `/v1/models` 不返回（`exposedModels()`）；
2. 不参与标签路由（`routeByLabel()` 末尾直接判 `null`，报错会提示「可能已屏蔽」）；
3. 不进同名自动路由的目录快照（`modelsStreaming()` 聚合时过滤，`updateModelBlocklist()`
   也就地裁掉已有快照）。

第 3 条最容易被漏掉：如果只在入口过滤，被屏蔽的模型仍会被当成跨供应商候选，
故障转移时又把它捡回来 —— 用户明明屏蔽了，请求却还是打到了它。

模型页 UI 仍展示全量（含已屏蔽的，整行降透明度 + 「已屏蔽」标签），
否则用户没法取消屏蔽。

屏蔽名单**不随目录刷新清理**：远端哪天把某个坏模型修好了，用户手动取消屏蔽即可，
不需要重配。

## 倍率、上下文与能力从哪来

各供应商给的信息口径不同，**有就显示、没有就不猜**（不拿常量表冒充上游数据）：

| 字段 | 来源 | 说明 |
|---|---|---|
| 倍率 `rate` | 腾讯（credits/tags）、字节（本地参考表）、讯飞（名字内嵌）、商汤（billing）、灵犀（`tokenRatio`） | 上游不提供的（谷歌 / ChatGPT / Cline / 自定义）不显示 |
| 上下文 `contextWindow` | 灵犀 `chat/config/get` 的 `maxInputLength`；ChatGPT `/models` | 其它家上游不给，界面不渲染该行 |
| 联网 `search` / 思考 `reasoning` | 灵犀 `chat/config/get` 的 `enableNetworkSearch` / `enableSetThinking` | 映射到模型页的「联网 / 思考」标记 |

### 灵犀（mCloud）的两个接口分工

- `POST /api/llm/apikey/get`：换长期 apikey + `modelUrl` + `modelList`（**只给倍率**）。
- `POST /api/outer/assistant/chat/config/get`：`modelList[].maxInputLength`（上下文）、
  `enableNetworkSearch`、`enableSetThinking`。请求头走主站来源（`Origin: https://yun.139.com`）
  与 `x-yun-api-version: v2`，和会员中心的 `vip.yun.139.com` / `v1` 不同，混用拿不到数据。
  两者共用同一套 Basic 凭证。

#### 两个必须踩准的坑（否则「接口通了但没有数据」）

1. **设备串是 WebView 形态，不是 App 原生形态**。抓包实测：
   - `x-DeviceInfo`：`||36|13.2.5||机型|uuid||android 16|||||`（第二段是 WebView 内核版本）
   - `x-yun-client-info`：`||1|13.2.5||机型|uuid||android 16|||||`

   设备标识是 **UUID**（`9a685a0e-…`），而 App 原生接口用的是 `5|127.0.0.1|1|…|32位hex|…`。
   发错形态时上游**不报参数错误**，而是回 `01000005「资源不存在」`——看起来像接口不存在。
   实现在 `MCloudDevice.webviewDeviceInfo` / `webviewClientInfo`。

2. **补拉依赖 Basic 凭证，而 Basic 只有 4 小时有效期**。老账号落盘时没有上下文，
   但它的 Basic 早已过期，直接补拉必然失败。所以补齐路径分三种：
   - Basic 还新鲜 → 直接补拉；
   - Basic 临期但可续 → 先 `refreshKey` 换新 Basic 再补拉（新 Basic 才有效）；
   - Basic 已彻底过期 → 不白等一次超时，记一条日志说明「续期或重新登录后自动补齐」。

   另外每次正常续期（`refreshKey → fetchKey`）都会顺带补拉，所以只要账号在用，
   上下文最终会补上。

`chat/config/get` 是**补充信息**，不是登录必需项：任何失败都只让模型少几个字段，
绝不中断登录或续期。补拉失败后冷却 30 分钟，避免上游长期不可用时每次刷新都白等超时。

## 模型行显示

- **模型名不带供应商前缀**：列表里显示模型本名（`ProviderModel.name`，空则回退 id），
  不显示 `供应商/` 前缀 —— 那是给下游客户端做标签路由用的标识，自己浏览时纯属噪音，
  且分组标题已经标明供应商。**复制仍给完整 `供应商/模型`**，`/v1/models` 与路由不受影响。
- **副标题只在有信息时渲染**：目前只承载上下文窗口（`contextWindow > 0`），
  上游没给就不占行，保持列表紧凑；不拿常量猜上下文。
- **测速上下两层**：上层是延迟数字（`<5000ms` 绿、否则橙），下层是相对时间
  （`刚刚` / `N分钟前` / `N小时前` / `N天前`）。相对时间来自持久化的 `testedAtMs`，
  老数据为 0 时不显示下层 —— 不假装刚测过。它只是展示层换算，不参与可用性判断。

## 一键测速与一键屏蔽

模型页头部两个图标按钮。测速成功/失败状态写入加密存储并跨重启恢复，包含最近一次结果与时间；「测试中」是瞬时态，不写盘。新一次测速完成后覆盖旧结果。模型页会明确提示这是**最近一次测速记录而非实时可用性保证**；分组统计沿用现有口径：成功计入测速成功，失败/未测计入待测，被屏蔽数单列。只有某供应商成功拉到新目录时，已下架模型对应的测速记录才会清理；拉取失败时保留。

- **一键测速**（⏱）：把当前列表里所有模型并发探一遍，并发上限
  `MODEL_TEST_PARALLELISM = 4`。每次探测都是一次真实上游请求，全量并发会在几十个
  模型时瞬间顶爆同一账号的限速阈值 —— 上游看到高频请求，反过来把整批测成 429，
  测出来的「失败」全是自己造的。结果逐条回写（CAS 合并，不是读改写回），
  所以界面能看到结果一条条亮起来。
- **一键屏蔽**（⊘，只在真有失败结果时出现）：把「测速失败」的模型一次性写进屏蔽名单。
  幂等，已在名单里的不重复计数，提示语报的是真正新增的条数。

单行 ⊘ 按钮用于就地屏蔽 / 取消屏蔽，方便测速失败后直接点。

## 目录快照：供故障转移零网络读取

`GatewayEngine.modelCatalogSnapshot` 保存**最近一次聚合成功的目录**，只用于
「按模型名自动跨供应商路由」（见 [05.容错机制.md](05.容错机制.md)）。

为什么不直接调 `models()`：

- 它会**真打每一家**上游接口（单家读超时 300s），只适合用户主动刷新或 `/v1/models`；
- 故障转移发生在「刚失败、正在重试」的路径上，此时现拉目录等于把一次超时放大成
  几十秒卡死 —— 越是在救火的时候越不能去做慢操作。

规则：

| 时机 | 行为 |
|---|---|
| `modelsStreaming()` 聚合成功 | 写入快照（覆盖） |
| 聚合结果为空（全部失败 / 无账号） | **不覆盖**，保留上一次有效快照 |
| 重启 | 清空，等下一次加载 |

**因此有一个使用前提**：开启「按模型名自动匹配」之前，至少要在模型页成功加载过一次
目录，否则快照为空、自动匹配不参与（请求行为退化成「不跨供应商」）。这不是 bug，
是刻意的 —— 拿空目录去猜同名模型，等于又回到「猜模型」。
