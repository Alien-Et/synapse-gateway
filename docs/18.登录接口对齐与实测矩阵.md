# 18. 登录接口对齐与设备侧实测矩阵（2026-11-18）

> **一句话结论**：登录链路的**请求形状已经和真机逐字段对齐**（query / body / 头 / Cookie / 顺序），
> 但在设备本机（中国移动出口 IP）实测仍然全部返回 `error_code=7「访问太频繁」`。
> 也就是说：**7 不是「接口没对齐」造成的**，而是发码业务侧按**设备 / 账号维度**做的频控。
> 本文把「对齐了什么」「怎么证明」「还剩什么」三件事钉死，避免下一轮再从零猜。

## 18.4 设备侧实测矩阵（全部在真机上、用 `/system/bin/curl` 直发）

| 组 | 形态 | HTTP | body | 裁决位 |
|---|---|---|---|---|
| E0 | 网关原样（无 guard / 无 Cookie） | 200 | `error_code=7` | `key-sign-result=2` `static-sign=1102` `static-ts=1102` |
| E1 | + 真机票据 7 个 guard 头 | 200 | `error_code=7` | `key-sign-result=3` `1104` `1103` |
| E2 | E0 + `x-tt-passport-mfa-token`（真机 SP 值） | 200 | `error_code=7` | 同 E0 |
| E3 | E0 + 登录态头（`x-tt-token` / `-supplement` / `session-tlb-tag` / `token-tlb-tag` / `key-sign`） | 200 | `error_code=7` | 同 E0 |
| E4 | E1 + 登录态头 | 200 | `error_code=7` | **`key-sign-result=0`** `1103` `1104` |
| E5 | E0 + `x-tt-passport-csrf-token` | 200 | `error_code=7` | 同 E0 |
| E6 | E2 + E3 | 200 | `error_code=7` | 同 E0 |
| E7 | 先 `GET account/info/v2` 拿 `odin_tt`（215 字符）→ 发码时带 `Cookie` | 200 | `error_code=7` | 同 E0 |
| E8 | `x-tt-request-tag: t=0;n=0` | 200 | `error_code=7` | 同 E0 |

### 读法

1. **E4 是决定性的一条**：guard 材料被服务端**完全接受**（`key-sign-result=0`，静态签名 1103/1104 已是「结构正确」档），
   业务层仍然回 7 ⇒ **7 不是 guard 校验失败**。
2. **E7 是第二条决定性证据**：带上真机同源的新鲜 `odin_tt` 会话 Cookie 仍然 7 ⇒ **7 不是「缺会话」**。
3. E0 的 `key-sign-result=2` 比 E1 的 `3` 更好，说明**直接回放真机票据反而被判为「旧票据」**；
   不带 guard 头时服务端只是把它当「普通匿名请求」，两者的 7 一模一样。
4. 换 `type`（24→25/26）能拿到 `3052` 而不是 7（历史实测，见 [豆包抓包/18.18](../豆包抓包/docs/18.设备票据生成逻辑.md)）⇒
   **7 是「登录验证码发码场景（type=24）」专属的业务频控**，不是全局拦截。

## 18.5 结论：7 到底是什么

`error_code=7` = **发码业务侧的设备 / 账号维度频控**，与下列因素**实测无关**：

- 出口 IP（本机为大陆移动 IP，仍 7）
- guard 头是否齐全、是否被接受（E1/E4 已到 `key-sign-result=0`）
- 会话 Cookie（E7 已带新鲜 `odin_tt`）
- csrf / mfa token / 登录态头 / request-tag（E2/E3/E5/E6/E8）
- 手机号（历史实测换新号同样 7）

**同一台设备上 App 能成功**，说明 App 手里有网关拿不到的东西。按排除法，剩下的只有两类：

| 候选 | 依据 | 可验证方式 |
|---|---|---|
| **A. TLS / HTTP/2 指纹** | App 走 TTNet(Cronet/BoringSSL)+HTTP/2；网关与 curl 都是 HTTP/1.1 + 另一套 TLS 指纹。前置风控完全可能按指纹分池 | 用 Cronet/OkHttp 发同一请求，看 7 是否变化 |
| **B. 完整 Cookie 集 + 真机 `klink_egdi`** | 真机 Cookie 是十几个 key 的集合（`ttwid` / `odin_tt` / `passport_csrf_token` / `d_ticket` / `s_v_web_id` …），本轮只补了 `odin_tt` 一个；`klink_egdi` 也仍是空 | 从真机 keva Cookie 存储导出整串回放 |

> ⚠️ 这两条都**不能靠「再对齐几个字段」解决**，需要换 HTTP 栈或做 Cookie 全量导出。

## 18.6 本轮代码改动的价值（与 7 无关，但都是真缺陷）

1. **发码请求此前完全不带 Cookie**（`post()` 从不设 `Cookie` 头）。真机 100% 带 —— 这是形状上的硬差异，
   已由 `DoubaoSessionCookieJar` + `bootstrapSession()` 修掉。
2. **没有会话初始化**：真机启动期先 `GET account/info/v2/?scene=normal` 拿 `odin_tt`，网关直接裸发码。
3. **`klink_egdi` 缺失**：已加参数位，但**只发真值**（默认空 = 不发），不复制别人设备的假值。
4. **错误信息不可诊断**：7 只回一句「访问太频繁」。现在会把 `key-sign-result` / `sign-res-static-sign`
   / `sign-res-static-ts-sign` 一起带出来，用户贴一张截图就能判断是「频控」还是「guard 被拒」。
5. **单测锁死 Cookie 协议纪律**：回带顺序、属性丢弃、空值不覆盖 —— 这三条错了不会报错，只会静默跑偏。

## 18.9 C 路线落地：从真机 keva 提取登录态（✅ 已打通，2026-11-18）

`error_code=7` 卡死手机号登录后，**导入真机登录态**是唯一立刻可用的路径。真机的 Cookie 不在任何明文文件里，
而在豆包 App 的 keva 存储：

```text
/data/data/com.larus.nova/files/keva/repo/ttnetKevaCookieStorage/
  ttnetKevaCookieStorage.blk   ← 记录体（Java 序列化对象 + keva 键）
  ttnetKevaCookieStorage.lxi   ← 索引（64B，未公开格式，**不需要**）
```

### 格式（实测）

每条记录 = `<keva 头> <0x81> <domain|/|name|0> <padding> <Java 序列化对象>`。
对象是 `SerializableHttpCookie` 的**自定义序列化**（`SC_WRITE_METHOD`、`fieldCount=0`），
字段按顺序写成 `TC_STRING` / `TC_BLOCKDATA` 流，**第一个 `TC_STRING` 就是 cookie 的值**；
值在文件里是 **URL 编码**的（`|`→`%7C`、`,`→`%2C`、`:`→`%3A`、空格→`+`）。
keva 是**追加写**，同名 cookie 有多条记录 → **取偏移最大的那条**。

> ⚠️ 踩坑：不要用「键后面的对象」做配对 —— 记录里键与对象的顺序不直观，配对会整体错位一位
> （第一次尝试就是这么错的，读出来的 `sessionid` 其实是 `d_ticket`）。
> 可靠做法是**按值形状识别**：`sid_guard` 一定长成 `<32hex>|<ts>|15552000|<GMT>`，
> 而它的前缀**就是** `sessionid` —— 这是唯一自洽的关系。

### 工具

[豆包抓包/scripts/keva_cookie_export.py](../豆包抓包/scripts/keva_cookie_export.py)：

```sh
python3 keva_cookie_export.py \
  /data/data/com.larus.nova/files/keva/repo/ttnetKevaCookieStorage/ttnetKevaCookieStorage.blk
```

输出一条可直接粘进「Cookie 导入」的串（实测 926 字符），包含
`sessionid` / `sid_guard` / `sid_tt` / `uid_tt` / `d_ticket` / `odin_tt` / `odin_tt_v2` /
`passport_csrf_token` / `store-region`。

### 有效性实测（容器直连，2026-11-18 13:24）

| 接口 | 结果 |
|---|---|
| `GET /passport/account/info/v2/?scene=normal` | **200**，返回 `app_user_info.profile_unique_name = one_cat`、`app_id=482431` |
| `GET /alice/call/quota` | **200**，`code=0` + 完整 `audio_quota_info` |

⇒ **这是一份真实可用的登录态**（2026-11-18 02:52 那次短信登录签发，`sid_guard` 有效期 180 天）。

### 导入方式

1. 导出串已写到手机 `/sdcard/Download/doubao_cookie.txt`（926 字节）；
2. 网关 → 供应商 → 豆包 → 「Cookie 导入」→ 粘贴 → 保存；
3. 保存后「刷新全部额度」能拉到额度即表示成功。

> 注意：这是**账号凭证**，等同密码。不要贴到聊天/日志/工单里；换设备或服务端轮换后需要重新导出。
