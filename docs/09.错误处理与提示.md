# 09. 错误处理与提示

## 错误分类

上游的失败先归到 `ErrorKind`，再决定重试策略：

| ErrorKind | 含义 | 处理 |
|---|---|---|
| `SESSION_DEAD` | 凭证失效（401，以及**非权限类**的 403） | 硬禁用该账号，换号 |
| `QUOTA` | 额度/积分耗尽（402） | 标记额度为 0，换号 |
| `SOFT_RATE` | 限流（429） | 退避重试，不累计错误次数 |
| `NOT_FOUND` | 模型不存在（404） | 换号或换供应商 |
| `MODEL_LIMIT` | 该 (供应商, 模型) 不可用（按账号计） | **先换同家其它号**；全试完才冷却该模型并告警。不计账号健康、不计熔断、不硬禁用 |
| `CLIENT` | 客户端问题（400/422） | **不该连累账号** |
| `SERVER` | 上游 5xx | 重试 |
| `NETWORK` | 连不上、超时 | 重试 |

### 403 不一定等于「凭证失效」

多数上游的 403 确实是令牌问题，但有例外：**「这个账号对这个模型没权限」也是 403**。

| 403 的含义 | 该归哪类 | 理由 |
|---|---|---|
| 令牌过期 / 被吊销 | `SESSION_DEAD` | 必须重新登录 |
| 账号对这个**模型**没权限（如 Cline 的 `ENTITLEMENT_ERROR`、`not subscribed to required model plan`） | `MODEL_LIMIT` | 换号可能有用（另一个号有订阅），重新登录解决不了 |

归错 `SESSION_DEAD` 的后果是**硬禁用账号** —— 用户看着「登录已失效」去重新登录，
登录完发现还是 403，因为他缺的是订阅不是凭证。

判据：错误体里出现 `entitlement` / `not subscribed` / `product surfaces` /
`no access to` 这类词时，按模型级权限处理。

## 对客户端的错误码

全部试完之后，按**出现次数最多**的主因映射（同票按严重度定序）：

| 主因 | 状态码 | 错误码 | 文案 |
|---|---|---|---|
| 无可用账号 | 503 | `no_healthy_account` | 没有可用账号（附池摘要） |
| 凭证全失效 | 401 | `all_accounts_unauthorized` | 所有候选账号的登录凭证都已失效 |
| 额度耗尽 | 429 | `insufficient_quota` | 所有候选账号的额度都已耗尽 |
| 限流 | 429 | `rate_limit_exceeded` | 上游限流：候选账号都在被限流 |
| 网络 | 502 | `upstream_unreachable` | 连不上上游：请检查网络或代理 |
| 上游 5xx | 502 | `upstream_error` | 上游服务异常 |
| 模型不存在 | 404 | `model_not_available` | 上游没有这个模型 |
| 模型不可用 | 429 | `model_unavailable` | 该模型在所有候选账号上都不可用 |
| 客户端问题 | 400 | `invalid_request` | 上游拒绝了该请求：参数或内容不合规 |

**「压根没账号」与「账号都在但都失败」分开**：从前两者都是 503
`no_healthy_account`，agent 端看不出到底是哪种。

## 对客消息的三段结构

```
真实主因；逐家原因｜涉及账号：账号A：原因；账号B：原因
```

账号明细单独成段：像「该模型在所有候选账号上都不可用」这种主因完全不提账号，
光看这句话根本不知道是哪个号被上游限了。

## 界面文案：不出现英文原文

网络异常一律翻成人话，原始报错只进日志：

```
界面上：连接「example.com」超时：上游在规定时间内没有响应。
        请检查网络，境外供应商可能需要开启代理

日志里：连接「example.com」超时：… ← failed to connect to
        example.com/1.2.3.4 (port 443) after 30000ms: ETIMEDOUT
```

覆盖六类：超时、连接被拒、网络不可达、DNS 解析失败、TLS 握手失败、连接中断。
已经是中文可读文案的异常（如「登录状态已失效」）直接原样显示，不再套壳。

### 上游错误体也要带中文语义

有些错误**不是网络问题**，而是上游用英文如实告诉你账号状态（402 余额不足、
403 没订阅）。这类不能只翻网络层，Provider 的 `classify()` 要负责补一句中文结论。

以 Cline 为例（`ClineProvider.explain()`）：

```
402 insufficient_credits
  → Cline 账户余额不足（已欠费或额度用完），当前余额 -0.002877 credit；
    充值地址 https://app.cline.bot/credits｜上游原文：Insufficient balance. ...

403 ENTITLEMENT_ERROR
  → 这个账号没有该模型的权限（通常是没订阅 ClinePass，或该模型不在套餐内）
    ｜上游原文：Error 403: the user is not subscribed to required model plan

401
  → Cline 登录凭证已失效，需要重新登录｜上游原文：Unauthorized: ...
```

三条规矩：

1. **中文结论在前，上游原文在后**（用 `｜` 分隔）。原文必须保留 ——
   排查时它是唯一能搜的线索。
2. **上游文案本身已是中文时不再套壳**（自定义中转站常见），原样返回。
3. **数字口径不能混**：402 错误体里的 `current_balance` 是 **credit**（`-0.002877`），
   而余额接口返回的是**微 credit**（`-17704`）。前者**绝不能再除 1e6**，
   否则会显示成 -0.000002 —— 看起来像余额是 0。

## actionHint 与 detail 的分工

| 字段 | 给谁看 | 内容 |
|---|---|---|
| `actionHint` | 普通用户 | 「打开哪个网址、验证完回来刷新」 |
| `actionUrl` | 界面按钮 | 可直接打开的 https 链接 |
| `detail` | 排查 | 含状态码、上游原文摘要 |

界面把 `actionHint` 单独排在前面并高亮，避免用户被一坨 JSON 劝退。

## 提示走系统接口

| 场景 | 用什么 |
|---|---|
| 短句 | 系统 Toast |
| 长句 | 系统对话框（跟随系统深浅色） |
| 强提醒 | 横幅 + 震动 + 常驻通知 |

**不用 Snackbar**——它会压在内容底部盖住按钮。

## 三种提醒机制

| 机制 | 文件 | 用途 | 频率 |
|---|---|---|---|
| 系统吐司 | `NoticeEvents.kt` | 一闪而过的状态提示 | 同 key 2 分钟去重 |
| 强提醒 | `QuotaAlerts.kt` | 额度耗尽、模型禁用 | 横幅 + 震动 + 常驻通知 |
| 实时通知 | `LiveStatusNotifier.kt` | 有请求在途时显示 | 随请求增减 |
