# 17. 设备证明链与 TEE

对应源码：`core/src/main/kotlin/io/synapse/core/provider/doubao/TeeKeyStore.kt`、
`Pkcs10.kt`、`DoubaoDeviceAttestation.kt`，单测 `DoubaoDeviceAttestationTest.kt`。

> 上游 SDK 的 `bdticketguard` 模块不是「可选项」，它是网关能不能被放行的关键之一。
> 本篇把它的**客户端侧**逐字节抄清楚，并说清哪些能复刻、哪些只能实测。

## 17.1 结论先行

**能复刻。** 上游那套设备证明链没有任何「只有它才能调」的私有能力：

| 环节 | 上游做法 | 复刻可行性 |
|---|---|---|
| 生成密钥对 | `KeyPairGenerator.getInstance("EC", "AndroidKeyStore")` | ✅ 公开 API |
| 密钥参数 | `KeyGenParameterSpec` 六件套（见 17.2） | ✅ 公开 API |
| 取证明证书链 | `KeyStore.getCertificateChain(alias)` | ✅ 公开 API |
| 设备证明 | `setAttestationChallenge(...)` → 证书链自带 Key Attestation 扩展 | ✅ 公开 API |
| CSR | **手写 ASN.1** + `SHA256withECDSA` | ✅ 纯编码 |
| 上报 | `POST security.snssdk.com/.../verify_pub_key/` | ⚠️ 见 17.4 |
| 每请求签名 | REE 软密钥（非 TEE） | ✅ 软密钥自持 |

容易误判的一点：**「私钥不可导出」不是障碍**。要用的不是上游的私钥，而是
**本机自己的** TEE 密钥——服务端登记的也是本机上报的公钥。上游私钥拿不到，
但根本不需要。

## 17.2 上游的密钥参数（逐条对照）

主签名密钥（`TeeApi.g`）：

```text
KeyGenParameterSpec.Builder(alias, PURPOSE_SIGN /* 4 */)
    .setDigests(["SHA-256"])
    .setAlgorithmParameterSpec(ECGenParameterSpec("secp256r1"))
    .setCertificateSubject(X500Principal("CN=" + alias))
    .setCertificateSerialNumber(BigInteger.ONE)
    .setCertificateNotBefore(Date(0))               // 1970-01-01
    .setCertificateNotAfter(Date(0x23d19d43c00))    // 2048-01-01
    .setUserAuthenticationRequired(false)           // 受远程开关 enableTeeKeyGenWithCert 控制
    .build()
```

**没有** `setIsStrongBoxBacked`、**没有** `setUnlockedDeviceRequired`、**没有**
`setInvalidatedByBiometricEnrollment` —— 不要自己加，加了会改变密钥落点。

attestation 密钥（`TeeApi.c`，多一行 `setAttestationChallenge`）：

```text
alias = "bd_ticket_guard_key_attestation"                  // 固定
challenge = SHA-256( teePubBase64 + "#" + reePubBase64 )   // 原始 32 字节，不是它的 base64
```

`challenge` 决定**是否要重建密钥**：与上次不同就必须 `deleteEntry` 再生成，
沿用旧 challenge 会被判重放（对应日志 `Key attestation, need regenerate, delete old key`）。

## 17.3 CSR 的精确形状

手写 `CertificationRequest`（RFC 2986）：

```text
SEQUENCE {
    certificationRequestInfo SEQUENCE {          -- version = 0
        INTEGER 0
        Name                     -- X500Principal("CN=" + alias).getEncoded()
        SubjectPublicKeyInfo     -- PublicKey.getEncoded()
        [0] IMPLICIT SET OF Attribute {
            SEQUENCE {
                OID 1.2.840.113549.1.9.14            -- extensionRequest
                SET { SEQUENCE {                     -- Extension
                    OID 2.5.29.19                    -- basicConstraints
                    OCTET STRING { SEQUENCE { BOOLEAN false } }
                } }
            }
        }
    }
    SEQUENCE { OID 1.2.840.10045.4.3.2 }         -- ecdsa-with-SHA256
    BIT STRING { <TEE 内签名> }
}
```

两个必须踩准的点：

1. **`ecdsa-with-SHA256` 的 AlgorithmIdentifier 不带 parameters**（RFC 5754）。
   抄 `sha256WithRSAEncryption` 的写法补一个 `NULL` 会被严格 DER 解析器拒绝。
   单测里把 `300A06082A8648CE3D040302` 锁死。
2. **签名前喂给 `Signature.update()` 的是 `CertificationRequestInfo` 的完整 DER**
   （含 tag 与长度），不是它的内容体。

输出 PEM（`-----BEGIN CERTIFICATE REQUEST-----`，64 列换行），与上游一致。

## 17.4 上报协议

三个端点都在安全域 `https://security.snssdk.com`（不是业务域，抓包时最容易漏）：

| 端点 | 作用 |
|---|---|
| `/passport/ticket_guard/get_client_cert/` | CSR 换 client-cert |
| `/passport/ticket_guard/verify_pub_key/` | 上报 TEE 证书链，服务端登记公钥 |
| `/passport/ticket_guard/attest_compensation_check/` | 事后复核 / 远程 invalidate |

`verify_pub_key` 的请求头（装配见 `DoubaoDeviceAttestation.buildVerifyHeaders`）：

| 头 | 值 |
|---|---|
| `bd-ticket-guard-attest-certs` | **base64(PEM 链按 `,` 拼接)** —— 整体再 base64 一次 |
| `bd-ticket-guard-ree-public-key` | REE 软密钥公钥（**裸点**，见下） |
| `bd-ticket-guard-client-cert` | **TEE 公钥裸点**的 `pub.` 封装（不是服务端下发的证书） |
| `x-tt-request-tag` | `t=0;n=0`（写死，不是随机值） |

**裁决只看响应头**：`bd-ticket-guard-verify-public-key-result` 是整数（0 = 通过），
响应体自始至终不参与判定。所以「HTTP 200 + 空 body」完全可能是失败，抓包必须抓响应头。
日志 ID 在 `X-Tt-Logid`。

### 业务请求头：逐字段对齐（真机抓包）

2026-11-16 用算法助手抓真机登录全程得到的地面真值。**登录前**（`send_code/v1`、
`account/info/v2`）与**登录后**（`security_token_beat`、`account/list`）带的头并不一样：

| 头 | 登录前 | 登录后 | 值 / 说明 |
|---|---|---|---|
| `bd-ticket-guard-tee-status` | ✅ | ✅ | `1` |
| `bd-ticket-guard-version` | ✅ | ✅ | `3` |
| `bd-ticket-guard-iteration-version` | ✅ | ✅ | `2`（登录后偶见 `3`） |
| `bd-ticket-guard-display-os-version` | ✅ | ✅ | `Build.DISPLAY`，如 `PJE110_16.0.5.1301(CN01)` |
| `bd-ticket-guard-client-cert` | ✅ | ✅ | `base64("pub." + base64(TEE 公钥裸点))`，外层 124 字符 |
| `bd-ticket-guard-ree-public-key` | ✅ | ✅ | `base64(REE 公钥裸点)`，88 字符 |
| `bd-ticket-guard-server-cert-sn` | ✅ | ✅ | `get_client_cert` 响应里的 `data.server_sn` |
| `bd-ticket-guard-client-data` | ❌ | ✅ | `base64(JSON)`，见下 |
| `bd-ticket-guard-key-sign` | ❌ | ✅ | `hex(64 字节)` |
| `bd-ticket-guard-attest-certs` | ❌ | ❌ | **只有 `verify_pub_key` 用** |
| `x-tt-request-tag: t=0;n=0` | ❌ | ❌ | **只有 `verify_pub_key` 用**（业务请求上是 `t=1;n=1`） |

**三个曾经判错、现已纠正的点**（都靠抓包地面真值纠正，记在这里防止再错一遍）：

1. **「登录前业务请求不带任何 guard 头」是错的。** 抓包脚本把两个头打印成一行
   （`HDR k1=v1: k2=v2`），只看行首会误读成「只有 4 个头」。实际 `send_code/v1`
   带齐了上面那 7 个 guard 头。
2. **公钥是裸点，不是 X.509 SPKI。** `bd-ticket-guard-ree-public-key` 解出来正好
   65 字节、首字节 `0x04`（base64 88 字符）；用 `publicKey.encoded`（SPKI，124 字符）
   发出去形状就不对。上游同一把密钥在 SP 里另存了一份 SPKI，只用于内部校验。
3. **`bd-ticket-guard-client-cert` 里装的是「TEE 公钥」，不是证书。** 解一层得
   `pub.` + base64，再解一层得 65 字节裸点。反编译侧的日志字符串写得很直白：
   `add TEE public key instead of cert`。

登录后才出现的两个头属于 v3 的**请求签名**，本项目的发码链路不经过它们，暂不复刻：

- `bd-ticket-guard-client-data` = `base64(JSON)`，字段 `req_content`（值是
  `"ticket,path,timestamp"`）、`req_sign`（base64 DER ECDSA，TEE 私钥签）、
  `req_sign_ree`（base64 裸 64 字节 `r‖s`，REE 私钥签）、`timestamp`、
  `ts_sign`（`"ts.1." + hex(64 字节)`）、`ts_sign_ree`（同前缀，REE 签）。
- `bd-ticket-guard-key-sign` = `hex(64 字节)`，与 `ts_sign` 的后 32 字节同尾。

**签名格式的不对称值得记一笔**：TEE 侧出来的签名是 **DER**（`SHA256withECDSA` 的
标准输出，`3044 0220…`），REE 侧是**裸 `r‖s` 64 字节**（软实现自己拼）——
从侧面印证两侧确实是「硬件签 + 软件签」两条路。

**角色的确认方式（可复算）**：真机 SP 里同时存着 TEE 证书（`client_cert_*`，其公钥
= `Build.DISPLAY` 那条链上的点）与 REE 私钥/公钥（`sp_key_private_key_ree_*` /
`sp_key_public_key_ree_*`）。把 REE 私钥在 P-256 上重推公钥，得到的结果与 SP 记录的
REE 公钥**逐字节一致** —— 这条推导链证明了「`ree-public-key` 头 = REE 软密钥」，
而不是 TEE 那把。


### 实测（2026-11-16，软密钥对照）

| 组 | 请求 | 服务端响应 |
|---|---|---|
| A | **不带** `bd-ticket-guard-attest-certs` | 裁决位 `1330`（拒绝），body `error_code=18000` |
| B | 带一张**软自签证书**（无证明扩展） | 裁决位**缺失**，body `message: exception` |

两条结论：

1. **服务端确实会解析这个头** —— B 组不是「拿不到裁决位」，而是服务端解析时直接异常，
   说明它真的在读证书链，不是走过场；
2. **「不带链」与「带假链」都会被拒** —— 所以「随便塞一张证书」走不通，必须给出
   结构合法的链。是否**必须是 TEE 真链**（能验到 Google 根 / 包名匹配），A/B 两组都证明不了，
   只能拿真机 TEE 证书链再测一次（见 17.7 未验证项）。

## 17.5 硬边界（必须实测才能确认）

1. **`attestationApplicationId`（包名 + 签名摘要）**
   Key Attestation 扩展里带调用方的**包名**与**签名证书摘要**，由系统（keystore2/TEE）写入、
   **应用无法伪造**。若服务端校验「包名必须命中白名单」，本项目（不同包名、不同签名）
   就会被拒。这是唯一真正可能挡住复刻的点，**只能拿真响应实测**。
2. **`get_client_cert` 的请求参数** —— 已拿到（见上面的业务请求头一节）：
   `POST /passport/ticket_guard/get_client_cert/`，query 与登录链同一套
   （`passport-sdk-version=60594&aid=482431&app_name=nova_ai&version_code=15070001&…`），
   body 是 `terminal_type=3&csr=<urlencode(base64(PEM))>&account_sdk_source=app&os_type=4&multi_login=1&server_data=1`；
   响应给 `data.cert`（客户端证书）与 `data.server_sn`（= 业务头的 `-server-cert-sn`）。
   实测**纯软密钥的手写 CSR 也能换到证书**，可见该端点不校验 CSR 是否出自 TEE。
3. **远程策略可收紧**：`attest_compensation_check` + 开关 `attestationEnableInvalidateQuery`
   允许云端事后作废已下发的 attest 结果。今天能过 ≠ 以后能过。

## 17.6 代码怎么接（已接线）

上游是「启动期 `loadTee()` 备密钥 → 请求期请求管线取头」两段式，本项目照同样的两段式接：

```kotlin
// DoubaoProvider：启动即备好设备密钥（等价 loadTee），请求期取头（等价请求管线）
private val authClient: DoubaoAuthClient = DoubaoAuthClient(
    guardHeaders = DoubaoDeviceAttestation().asGuardHeaders(),
)
```

`DoubaoDeviceAttestation` 内部三段：`prepare()`（两把 TEE 密钥 + challenge + 证书链）、
`enrollClientCert()`（CSR 换 client-cert，带缓存，同时收下 `server_sn`）、
`asGuardHeaders()`（按抓包对齐注入 **7 个头**：tee-status / version / iteration-version /
display-os-version / client-cert / ree-public-key / server-cert-sn）。

**两组头是分开的**，别混：`asGuardHeaders()` 服务业务请求（登录前那一套）；
`buildVerifyHeaders()` 只服务 `verify_pub_key`，多带 `bd-ticket-guard-attest-certs`
与 `x-tt-request-tag: t=0;n=0` —— 这两个头出现在业务请求上反而是特征差异。

**行为纪律（单测锁死）**：TEE 不可用、公钥取不出、enroll 失败 —— 任一发生就返回空 map，
与接线前完全一致。发码链一行都不用改。

> 注意 `:core` 是纯 JVM 模块，`android.security.keystore.*` 通过**反射**访问 —— 同一份
> 字节码既能在设备上真正生成 TEE 密钥，也能在本机跑单测（在 JVM 上安静地报告「不可用」）。
>
> 接线前这三个类是**死代码**：R8 的 shrink 会把它们整个删掉（表现为编译成功但 APK 的
> SHA-256 一个字节都没变）。接线后 APK 增量约 **14 KB**。

## 17.7 已验证与未验证

已验证（本机可跑，`DoubaoDeviceAttestationTest`）：

- OID / DER 长度段编码（`06 03 55 1D 13`、`06 08 2A 86 48 CE 3D 04 03 02` 等锁死）；
- 生成的 CSR 能被自己的公钥**独立验签**，篡改一字节后验不过；
- `attributes` 里确实带 `extensionRequest` + `basicConstraints`；
- PEM 反解回原 DER；
- challenge 派生 = `SHA-256(teePub#reePub)`；
- 裁决位大小写不敏感解析、缺位/非整数的失败判定；
- 裸点编码 = 65 字节（`04‖X‖Y`，base64 88 字符），且与「从 SPKI 尾部切 65 字节」的
  回退路径逐字节一致；
- `client-cert` 头是**两层**封装（外层 124 字符 → `pub.` + 内层 base64 → 65 字节裸点）；
- JVM 上 `TeeKeyStore.isAvailable() == false`、`asGuardHeaders()` 返回空头、
  `displayOsVersion()` / `serverCertSn()` 返回空串（对应头自动省略）。

顺带确立的两条（软密钥就已跑通）：

- `get_client_cert` 用**纯软密钥**的手写 CSR 就能换到证书（HTTP 200 + 下发 `cert`）
  → 该端点不校验 CSR 是否出自 TEE；
- `verify_pub_key` 的 A/B 组裁决（见 17.4 实测表）→ 服务端会真解析证书链。

未验证（需要设备 + 真实会话）：

- 设备上生成 TEE 密钥、拿到带 Key Attestation 扩展的证书链；
- 服务端对 `io.synapse.app` 这个 `attestationApplicationId` 的裁决（A/B 组只能证明
  「假链不行」，不能证明「真链一定行」）。

## 17.8 设备侧确认方法

要确认「本项目自己在 AndroidKeyStore 里能生成密钥并取到证书链」，最省事的路径是
Frida attach 到**本项目自己的进程**后跑一段 Java 调用：

```text
KeyStore.getInstance("AndroidKeyStore") → load(null, null)
反射 KeyGenParameterSpec$Builder(alias, 4) → setDigests/setAlgorithmParameterSpec/setAttestationChallenge
KeyPairGenerator.getInstance("EC","AndroidKeyStore").generateKeyPair()
KeyStore.getCertificateChain(alias)
```

重点看三个量：链长、叶子证书是否带 `1.3.6.1.4.1.11129.2.1.17`、
扩展里的 `attestationApplicationId` 包名。

注意：`frida-server` 走 `127.0.0.1:27042`，客户端版本必须与 server 一致；
LSPosed 作用域注入那条路对**本项目**不适用（作用域里没有它，写开关也不会注入）。
